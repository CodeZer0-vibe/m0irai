**THESIS:** zer0 chat should not feel like “three chatbots in one terminal.” The winning experience is a mission-control TUI where the human gives one intent, the system fans work out to three independent lanes, and the UI collapses their noise into one coherent command log, one review surface, and one quota-aware routing brain. The core design move is ruthless: live agent streams are secondary instrumentation; completed deltas, blockers, risks, diffs, and required human decisions are primary.

## Evidence Base

I used current public sources and user discussions. A few anchors:

Anthropic explicitly frames parallel agent work as choosing whether “you want to stay in each conversation yourself” or “hand tasks off”, and recommends worktrees so parallel sessions “never edit the same files”.

Google positions Gemini CLI partly around quota: “60 model requests per minute and 1,000 requests per day”, and even names “professional developer[s] who need to run multiple agents simultaneously”.

Anthropic published the adoption trap: “Claude Code users approve 93% of permission prompts” and says this creates “approval fatigue”.

Zed’s ACP work is the best external design clue: terminal agents need structured UI beyond ANSI logs, enabling “real-time edit visualization, multi-buffer reviews”.

## Thrust 1: Users And The Ideal Terminal Experience

### 1. How Power Users Combine Agents Today

The real workflows are not philosophical “multi-agent debate.” They are pragmatic labor arbitrage.

Pattern one: premium builder plus cheaper scout. Claude or Codex gets the hard implementation. Gemini gets codebase reconnaissance, docs search, summarization, test-output triage, or “read the whole repo and tell me where the risk is.” Google’s own launch copy leans into Gemini as a broad terminal utility for “content generation, problem solving to deep research and task management”.

Pattern two: builder and adversarial reviewer. The cleanest observed pattern is: Agent A implements, Agent B reviews the diff cold, Agent C arbitrates or tests. This appears in public tools like Mysti, whose pitch is two agents “debate approaches, then synthesize”, and Roundtable, whose example routes Gemini to performance/UX, Codex to TypeScript/code quality, Cursor to accessibility/SEO, and Claude to business logic.

Pattern three: parallel worktrees. Advanced users already run multiple terminal tabs, tmux/Zellij panes, or IDE sessions. Claude’s docs validate that model: worktrees isolate parallel sessions. This is important because multi-agent coding without file isolation becomes merge-conflict roulette.

Pattern four: rate-limit overflow. This is a huge driver, not a side benefit. Gemini’s generous free quota is product strategy. Anthropic’s rate-limit docs say limits are per model and can be used “simultaneously” across models. Users naturally learn to preserve expensive Claude turns for high-leverage work and spend cheap/free turns on exploration.

Pattern five: same prompt, independent opinions. For architecture decisions, people want blind second opinions. The value is not three identical completions; it is model-diverse disagreement before the human commits.

### 2. What Developers Want

Stated desires:

- Use existing subscriptions and local auth.
- Stop copying context between terminals.
- Keep agents isolated but coordinated.
- See usage, spend, remaining quota, and reset time.
- Keep a shell available while an agent works.
- Review changes like a PR.
- Resume sessions after terminal close.
- Use one agent while another is busy.

Unstated desires:

- A confidence machine. They want the product to tell them: “this changed these files, tests passed, Codex objected here, Claude agreed here, Gemini found no broader repo issue.”
- A blame map. When something breaks, they need to know which agent changed what and why.
- Permission sanity. They do not want to choose between being interrupted every 20 seconds and giving a model unsafe full access.
- Tasteful quiet. They want the power of three agents, not the visual feeling of three interns yelling in Slack.

### 3. Why They Abandon

The abandonment triggers are predictable:

Approval fatigue. Anthropic’s 93% approval statistic is the smoking gun. A prompt that always gets accepted is no longer safety; it is UI tax.

Unreadable output. Three long streaming answers in one terminal is not “powerful,” it is attention denial. Once the user cannot reconstruct who did what, trust collapses.

Lost context. If every lane needs re-explaining, users go back to separate tools where at least the failure is familiar.

Cost surprise. Multi-agent tools multiply token burn. If cost/quota is not visible before dispatch and during execution, users feel tricked.

Write conflicts. Any cockpit that lets three agents edit the same files without worktree or patch isolation is unserious.

Weak review surface. Users do not want to read prose after an autonomous run; they want changed files, diff hunks, tests, risks, and accept/reject controls.

Setup friction. API keys, hidden auth state, model-specific config, and broken Windows behavior will kill adoption before the product proves value.

### 4. The Ideal Cockpit

The dream screen is not three equal panes. It is:

Top strip: mission, branch/worktree state, active agents, quota burn, next reset.

Center: one chronological command log made of task cards, not raw streams. Each card has agent identity, phase, elapsed time, files touched, confidence, and latest meaningful event.

Right or bottom rail: live lane status. Claude planning, Codex editing, Gemini researching. Small, glanceable, interruptible.

Focused view: pressing enter on a card opens the full transcript, tool calls, files read, commands run, and raw output.

Review mode: one synthesized PR-style surface: summary, changed files, combined diff, test results, per-agent objections, unresolved questions, accept/reject/apply controls.

Router: `@all` should ask whether this is debate, parallel implementation, review, research, or overflow. Do not make the user manually choreograph every time.

### 5. Usage, Cost, And Rate Limits

This is one of the top three reasons the product exists.

A second or third agent is often justified by one of four economics:

- Preserve premium Claude turns.
- Use Gemini’s generous quota for broad/cheap work.
- Use Codex for lower-cost deep repo or review work.
- Continue working while one provider is rate-limited.

The UI should treat quota like CPU in `btop`: always visible, never dominant until it matters. Show estimated burn before dispatch, current burn while running, and “recommended cheaper lane” when a task is low-risk.

### 6. Notifications: Interrupt Vs Ambient

Interrupt only when human action changes the outcome:

- Approval required for risky command, external network, secret access, deletion, migration, install, or write outside workspace.
- Agent blocked.
- Test failed after claimed fix.
- Merge conflict or overlapping file ownership.
- Cost threshold crossed.
- Security or data-loss risk detected.
- All agents complete and review is ready.

Keep ambient:

- Token streaming.
- File reads.
- Routine command progress.
- “Thinking,” “planning,” “searching.”
- Non-actionable summaries.
- Minor quota movement.

Microsoft’s notification guidance is exactly right here: notifications should “save time” and not “distract or create more work”.

## Thrust 2: Combining And Displaying Three Elite Agents

### 1. Attribution And Separation

For long text in constrained width, the best default is a single chronological log of block-level agent cards with persistent left rails, not side-by-side panes.

Comparison:

Colored left rails/gutters: best primary attribution. They survive long text because the user’s eye can scan the left edge. But color must be redundant with labels and symbols.

Header lines: mandatory. Each block needs `CLAUDE | planning | 2m14s | 3 files | $0.42 est`. The header is the contract.

Prefixes/sigils: useful for dense logs, weak for paragraphs. Good for one-line events, not enough for long reasoning.

Side-by-side panes: good for short live monitoring, bad for long prose. Three columns in a Windows terminal produce unreadable line wraps.

Single interleaved token stream: worst option. It creates false simultaneity and destroys comprehension.

Tabs: good for raw detail, bad for situational awareness. Hidden lanes feel frozen or forgotten.

Best model: one main chronological feed, one compact lane monitor, full-screen drilldown per agent.

### 2. Information Hierarchy

Primary:

- Current mission.
- Agent cards with decisions, blockers, changed files, test outcomes.
- Final synthesis and review queue.

Ambient:

- Spinner/progress.
- Elapsed time.
- quota/cost.
- queue length.
- current phase.

On-demand:

- Raw transcripts.
- tool call details.
- full stdout/stderr.
- files read.
- token accounting.
- alternative agent drafts.

This follows progressive disclosure: NN/g says if something appears initially, users infer “it’s important”. Do not show raw model monologue by default unless the user is in debug mode.

It also follows Gestalt proximity: nearby elements are perceived as related. Each agent block needs tight internal grouping and clear whitespace between blocks. Borders everywhere are visual debt; spacing does more work.

### 3. Legibility Craft

Body text must use the terminal’s normal foreground or a verified high-contrast neutral. Do not paint body text in agent colors.

Agent colors should be accents only: rail, small badge, status dot. The moment every paragraph is cyan/purple/yellow, the product becomes less legible and less trustworthy.

For arbitrary or transparent backgrounds:

- Prefer no filled backgrounds for body cards.
- Use ASCII/box borders sparingly.
- Use bold/weight and spacing before hue.
- Never rely on red/green alone.
- Offer high-contrast mode and monochrome mode.
- Keep semantic colors stable: red only risk/fail, amber blocked/warn, green complete/pass, blue informational.

WCAG’s baseline is useful even in terminal land: normal text generally needs 4.5:1 contrast. Since transparent terminals can sit over anything, assume the background is hostile.

Julia Evans’ terminal color warning matters too: ANSI colors are user-remapped; terminals have “16 numbered colours” with local meanings. Use truecolor carefully, but also support no-color and user-theme modes.

### 4. Making Three Agents Feel Like One Super-Agent

The composition should say: one mission, three lanes, one verdict.

Do not brand the experience around agent personalities. Brand it around team capability:

- One shared memory panel.
- One task graph.
- One review queue.
- One final synthesized recommendation.
- One “apply accepted changes” flow.
- One audit trail.

The agents should feel like specialists behind a single cockpit, not celebrities competing for screen time. Let the user address Claude/Codex/Gemini when needed, but default to role routing: `research`, `build`, `review`, `test`, `summarize`, `debate`.

### 5. TUIs To Copy

Zellij: copy panes/tabs/session persistence, but not the idea that panes are the main information architecture. Zellij describes panes, tabs, sessions, layouts, and plugins as a workspace layer. zer0 should use that mental model internally.

lazygit: copy keyboard-first review. Lazygit makes staging a line-level action with space/enter/tab flows. zer0’s diff review should feel that direct.

k9s: copy status-aware navigation and command discoverability. K9s “continually watches Kubernetes for changes” and offers commands against observed resources. zer0 should continually watch agent state and expose legal actions per selected card.

btop: copy dense ambient telemetry. `btop` works because graphs and numbers are glanceable, not because everything demands attention. It offers “real-time visualization” of CPU, memory, disk, network, and processes. zer0 should do the same for agent lanes and quota.

Zed ACP: copy the review model. Zed lets users “follow the agent in real time” and then “review code like a pull request”. That is the gold standard for autonomous coding UX.

Codex CLI: copy dedicated review presets. Codex `/review` reads selected diffs and reports “prioritized, actionable findings” without touching the tree.

### 6. Review/Diff Surface

The best model is PR review, not chat history.

After an autonomous run, the default screen should be:

- What changed: concise summary by feature/behavior.
- Files changed: grouped by agent and by subsystem.
- Diff: unified, syntax-highlighted, file-by-file.
- Tests: commands run, pass/fail, raw logs folded.
- Objections: each agent’s review findings, deduped.
- Risks: migrations, secrets, network, deleted files, untested paths.
- Controls: accept file, reject file, open hunk, ask agent to fix finding, create patch branch, discard lane.

For multi-agent output, never make the human reconcile three prose summaries manually. The cockpit should synthesize, then preserve dissent.

### 7. Per-Agent Independence

The UI should express each agent as a lane with its own lifecycle:

`idle -> queued -> planning -> waiting approval -> editing -> testing -> reviewing -> complete -> blocked`.

The composer should support target routing:

- `@all`: broadcast/debate.
- `@free`: send to any idle/cheap lane.
- `@codex`: direct.
- `@gemini while claude runs`: explicit overflow.
- `@review`: dispatch reviewer against current diff.

Busy lanes should not block the composer. A long Claude run should leave Codex and Gemini usable. Queueing should be visible per lane, with cancel/reprioritize controls.

## Top Recommendations (Ranked)

1. Build the UI around task cards, not chat streams. Raw streaming output should be collapsible instrumentation.

2. Use a single chronological command log with persistent left rails, headers, and agent badges. Avoid three equal long-text panes.

3. Add a compact lane monitor for Claude/Codex/Gemini with phase, elapsed time, queue, touched files, and quota burn.

4. Make review mode the hero surface: changed files, diff, tests, findings, risks, accept/reject.

5. Route by role by default: scout, builder, reviewer, tester, synthesizer. Let users override by agent name.

6. Treat quota as first-class telemetry. Show estimated burn before dispatch and live burn during work.

7. Use worktree or patch isolation for concurrent edits. No shared-file free-for-all.

8. Implement notification severity. Interrupt only for decisions, risk, blockers, test failure, cost threshold, or completion.

9. Design for hostile terminal backgrounds. Neutral body text, minimal accent color, no color-only meaning, high-contrast and monochrome modes.

10. Preserve dissent. Final synthesis should say where agents disagree instead of flattening everything into false consensus.

## What Everyone Gets Wrong

Most multi-agent tools think the product is “more agents visible at once.” Wrong. The product is fewer human decisions per unit of verified progress.

The trap is building a three-pane slot machine: Claude says a lot, Codex says a lot, Gemini says a lot, and the user becomes the merge algorithm. That feels powerful for five minutes and then collapses into noise, cost anxiety, and distrust.

The correct cockpit hides most of the agent chatter, exposes the audit trail on demand, and makes the human review concrete artifacts: diffs, tests, blockers, risk, and disagreement. The point of three elite agents is not three times the text. It is one stronger engineering judgment with receipts.
