## TL;DR (read this first)

1. **The ACP protocol itself (`@agentclientprotocol/sdk` 1.2.1) supports live, mid-session mode switching** via `session/set_mode`, explicitly documented as callable "at any point during a session, whether the Agent is idle or generating a response." Both installed ACP bridges — `claude-agent-acp` 0.58.1 and `codex-acp` 1.1.2 — **implement it for real** (not a stub): claude routes it to the Claude Agent SDK's `Query.setPermissionMode()`; codex mutates `sessionState.agentMode`, which is re-read fresh on every `prompt()` call and threaded straight into the next `runTurn()`'s `approvalPolicy`/`sandboxPolicy`.
2. **zer0's own ACP wiring never calls it today.** `src/adapters/acp/acp-turn-session.ts`, `acp-lane-session.ts`, and `acp-lane-connection.ts` open sessions and stream prompts but contain zero references to `setSessionMode` / `session/set_mode` / `SessionModeState`. The permission decider is hardcoded to `autoApproveDecider` (auto-allow everything) everywhere. So today: the wire-level capability exists in the installed bridges, zer0 just isn't using it.
3. **gemini has no ACP at all** (confirmed in zer0's own code comments and empirically in the team's 2026-06-17 probe doc — `GitHub issue #31 open` against `--acp`). The "gemini chair" is `agy` (Antigravity CLI, v1.1.3), driven either as a one-shot headless `--print` child (today's default, in-cockpit path) or as a full raw ConPTY passthrough to agy's own native TUI (`zer0 agy`, built but **not yet embedded in the chat cockpit** — its own header says so).
4. **BLOCKING DISCOVERY for W4: Shift+Tab is not free.** It is already live-bound in zer0's shipped cockpit keymap (`src/tui/use-cockpit-keymap.ts`) to cycle the **RMODE** (diff-review surface: full → notify-only → off), an operator-locked decision from 2026-07-11, checked _first_, before every other handler, and _always consumed_ even when unwired. W4 cannot silently repoint Shift+Tab to native-engine-mode cycling without colliding with this existing, shipped, operator-approved feature. See "Open questions" below — this is not mine to resolve.

**Live mid-session switch — the mechanism, exactly:**

- ACP wire: `session/set_mode` (`AGENT_METHODS.session_set_mode`) → agent handler `setSessionMode(params)` at `acp-agent.js:2039-2053` → `applySessionMode(sessionId, modeId)` at `acp-agent.js:2141-2175` → `await session.query.setPermissionMode(modeId)`.
- SDK primitive: `Query.setPermissionMode(mode: PermissionMode): Promise<void>` — doc comment at `claude-agent-sdk/sdk.d.ts:2245-2251`: _"Change the permission mode for the current session. Only available in streaming input mode."_ `PermissionMode` type at `sdk.d.ts:2043`: `'default' | 'acceptEdits' | 'bypassPermissions' | 'plan' | 'dontAsk' | 'auto'`.
- Protocol doc confirms mid-_turn_ legality, not just mid-session: ACP spec at agentclientprotocol.com/protocol/session-modes — _"This can occur at any point during a session, whether the Agent is idle or generating a response."_
- Zer0's own installed SDK client type (`@agentclientprotocol/sdk/dist/acp.d.ts:1097-1112`) exposes the client-side call: `setSessionMode(params: schema.SetSessionModeRequest): Promise<schema.SetSessionModeResponse>` with the same "at any time" doc comment.

**What zer0 sends today, quoted:**

- Headless dispatch (`src/adapters/claude.ts:152-173`, function `claudeArgsFor`) — for chat/research/build: hardcoded `--permission-mode bypassPermissions`, no operator choice, no live switching (fresh process per turn, killed after). For the undefined/review path: no `--permission-mode` flag at all (defaults to claude's own default, i.e. `default`/"Manual").
- ACP lane sessions (`src/adapters/acp/acp-turn-session.ts:110-227`, `acp-lane-session.ts`, `acp-lane-connection.ts`): **no `--permission-mode` equivalent is ever set.** No call to `setSessionMode` anywhere in these files (confirmed by grep across `src/adapters/acp/`). The permission mode the ACP session actually runs under is whatever `resolvePermissionMode` resolves from the mirrored `settings.json`'s `permissions.defaultMode` key in the zer0-owned `CLAUDE_CONFIG_DIR` (`acp-clean-config.ts:41`, `DROP_KEYS` does **not** strip `permissions`, so the operator's real `~/.claude/settings.json` permission default flows through unless they've set one — if unset, claude's own default is `"default"`/Manual). Every permission _ask_ is then auto-approved regardless of mode via `autoApproveDecider` (`acp-permission.ts:26-29`), which is a structurally different lever from _which_ mode is active.

**Live-cycling feasibility: YES.** Both the wire protocol and the underlying SDK explicitly support calling `setSessionMode` mid-turn. zer0 would need to (a) thread a `setSessionMode` call through `TurnSession`/`LaneSession` (neither interface currently exposes one — `TurnSession` only has `prompt`/`close`; `LaneSession` only has `prompt`/`close`) and (b) track `currentModeId`/`availableModes` from the `newSession`/`resumeSession` response (`NewSessionResponse.modes?: SessionModeState`, `types.gen.d.ts:2568`) which zer0 currently discards entirely (`acp-lane-connection.ts:103-109` only extracts `sessionId` from the response).

Real CLI's broader `approval_policy` enum (from installed `codex --help`, top-level `-a/--ask-for-approval`) is **wider** than what the bridge exposes as named modes: `untrusted` (auto-run only a "trusted" allowlist like `ls`/`cat`/`sed`, else ask) / `on-request` (model decides when to ask) / `never`. The bridge's three presets use only `on-request` and `never` — **`untrusted` is not reachable as a named ACP session mode today**, only via raw `-c approval_policy=untrusted` config override (not exposed over `session/set_mode`).

**Live mid-session switch — the mechanism, exactly:**

- `setSessionMode(_params)` at `index.js:28139-28148` → `applyModeChange(sessionState, modeId)` at `28193-28199` → `sessionState.agentMode = newMode` (pure in-memory mutation, no respawn).
- **Confirmed re-read per turn, not just per session:** inside the prompt handler, `const agentMode = sessionState.agentMode;` at `index.js:28889`, passed straight into `sendPrompt(...)` → `runTurn({ approvalPolicy: agentMode.approvalPolicy, sandboxPolicy: … })` at `index.js:25898-25907`. This means `runTurn` (codex's own protocol call) carries approval/sandbox **per turn**, not fixed at process/session spawn — so a `session/set_mode` call between turn N and turn N+1 changes what turn N+1 actually runs under, no restart required.
- Mode is _also_ mirrored into the legacy `session/set_config_option` surface under `MODE_CONFIG_ID` (`index.js:28160-28162`, `applyModeChange` shared with the native path) — the bridge maintains a dual protocol surface (native `session/set_mode` for ACP-modes-aware clients, `set_config_option` fallback for clients that only understand config options).

**What zer0 sends today, quoted:**

- Headless dispatch (`src/adapters/codex.ts:115-131`, `buildCodexCommand`): `codex exec --sandbox <workspace-write|read-only>` chosen ONLY by `chatMode === undefined` (read-only, review path) vs everything else (workspace-write). No `--ask-for-approval` flag ever passed (codex's own default applies — `on-request` per its CLI help). No live switching; one-shot process per turn.
- ACP lane sessions (`acp-turn-session.ts`, `acp-lane-session.ts`): same as claude — **no `setSessionMode` call anywhere.** Whatever mode the codex-acp bridge defaults new sessions to (its own default — the bridge's `DEFAULT_AGENT_MODE = _AgentMode.Agent`, i.e. workspace-write/on-request) is what every zer0 ACP codex turn runs under, permanently, for the life of the lane session.

**Real CLI's own interactive keybinding (for context, not what zer0 currently drives):** confirmed via a live GitHub issue against `openai/codex` — **openai/codex#9766**, titled _"Shift+Tab mode toggle resets model to gpt-5.2-codex; multi-agent cannot choose model or reasoning depth"_ — which presupposes Shift+Tab-driven mode toggling exists as a real, in-use feature of the interactive `codex` TUI (the issue is about a bug in that toggle's side effects, not disputing the toggle's existence). Secondary sources also describe a `/approvals` (or `/permissions`, naming inconsistent across sources — see Unverified) slash command as an alternate path. **I could not fetch OpenAI's own canonical page confirming the exact keybinding** (the two most relevant doc URLs 404'd / redirected to a page that didn't render the specific section); this is corroborated by one primary-ish source (the GitHub issue) and multiple secondary blog/cheat-sheet sources, not a directly-quoted first-party doc page.

**Live-cycling feasibility: YES**, and more cleanly than claude's — the bridge already re-reads `sessionState.agentMode` fresh every turn, so a `session/set_mode` call any time before the _next_ prompt is guaranteed to take effect on that next turn. (Mid-_generation_ live switching, i.e. changing approval policy while a turn is actively streaming, is not demonstrated either way — `runTurn`'s policy is bound at the moment that specific turn starts, per the code above; this is a between-turns guarantee, not necessarily a mid-turn one, which is a lower bar than claude's SDK-level claim but still fully sufficient for a Shift+Tab-between-messages UX.)

## Open questions the W4 design round must decide

1. **The Shift+Tab collision (blocking).** `src/tui/use-cockpit-keymap.ts:12-15,68-111` already binds Shift+Tab, globally, composer-scope, checked first, to cycle RMODE (`src/chat/review-mode.ts`: full → notify-only → off), an operator-locked decision dated 2026-07-11 with its own persisted state (`.zer0/review-mode.json`). RMODE governs the _operator's own review/approval surface_ across all agents; W4's native-mode-cycle governs _what each engine's process is allowed to autonomously do_. These are different axes that both want the same key. Options are for the design round to pick, not for this research to presume: reuse a different modifier/key, make Shift+Tab context-dependent on focus, fold RMODE into the same picker as engine-mode, or something else — the point of this doc is only that the collision is real and must be resolved explicitly, not silently overwritten.
2. **Per-engine mode vocabularies do not line up 1:1.** claude has 4-6 modes (default/acceptEdits/plan/dontAsk/bypassPermissions/auto, 2 gated), codex-acp exposes exactly 3 curated presets (a subset of the real CLI's broader approval_policy × sandbox_mode matrix), agy exposes 2 explicit `--mode` values plus an implicit default plus 2 more orthogonal flags (`--sandbox`, `--dangerously-skip-permissions`) that aren't part of `--mode` at all. A single unified "cycle" affordance needs a decision on whether it cycles each engine's _own_ native list (different length/order per engine) or a zer0-normalized subset common to all three.
3. **claude/codex: the wiring gap is real but bounded.** `TurnSession` and `LaneSession` (`acp-turn-session.ts`, `acp-lane-session.ts`) would need a new method (e.g. `setMode(modeId)`) added to their interfaces and real deps, plus `SessionModeState` needs to be captured from `newSession`/`resumeSession` responses (currently discarded — only `sessionId` is extracted, e.g. `acp-lane-connection.ts:103-109`). This is incremental, not a rearchitecture.
4. **agy: there is no live session to cycle a mode within, today, in the cockpit.** Whether W4 wants to (a) embed the interactive-passthrough engine into the cockpit (raw keystrokes to agy, zero zer0 visibility into current mode — the passthrough's own header already earmarks this as future work), (b) extend the one-shot dispatch to accept a `--mode` argument threaded per-turn (turn-granular "live" switching, consistent with how `--conversation` continuity already works), or (c) leave gemini out of the unified Shift+Tab affordance entirely, is unresolved and has real UX consequences (gemini would behave differently from the other two chairs either way).
5. **`src/tower/adapter-gemini.ts` currency is unconfirmed.** It targets the raw `gemini-cli` bundle, not agy, and no `@google/gemini-cli` dependency exists in `package.json` today. Confirm with whoever owns Tower whether this file is dead/pending-deletion or actually still reachable through some path I didn't find, before assuming it's a live alternative surface for gemini modes.
