# zer0 chat — Design craft for a 3-agent terminal cockpit

Independent research stream. Topic: how to display dense, **concurrent**, multi-stream output in a terminal so that three elite agents (Claude, Codex, Gemini) read as **one coherent super-agent**, not three cramped windows.

Method: live web sources (WebSearch/WebFetch June 2026) + design-principle literature + my own TUI design knowledge. Non-obvious claims carry a URL + quote. `INFERENCE` marks my own synthesis not lifted from a source. No source was hard-blocked; one access-note below.

Access-note: Warp's _"the data structure behind terminals"_ page is engine-internals only — it does **not** discuss UX, so I pulled UX claims from the docs + the _agentic block model_ post instead.

---

## 0. Thesis up front (my independent verdict)

For **three concurrent long-form streams** on a single Windows terminal of typical width (80–120 cols), the architecture choice is forced, and the popular answers are wrong:

- **Side-by-side panes fail.** Three columns = ~30–40 cols each. Code, diffs, and stack traces hard-wrap into garbage. This _is_ the "three cramped windows" failure the brief names. Panes are right for _peers of similar, short, tabular content_ (k9s, lazygit) — not for three independent prose+code firehoses.
- **Tabs hide concurrency.** One-agent-at-a-time defeats the entire premise ("feel like one team", and the operator's INV-0: use free agents while one is busy). You cannot supervise what you cannot see.
- **The winner is a single chronological interleaved log with ruthless per-agent attribution, where each agent turn is a foldable _block_.** One timeline = one team. Attribution carries the "who" so the single column never confuses you. Folding keeps three firehoses from becoming a wall of text.

Plus one always-present **ambient status strip** showing all three agents' live state at once (thinking / streaming / idle / usage%), so you keep peripheral awareness of agents whose output isn't currently scrolling. **One primary timeline + one ambient roster = the cockpit.** This is essentially the team's "Anchored Gutter" direction, and the evidence below converges on it independently.

The rest of this report is the evidence and the craft to execute it.

## 1. The core architectural decision: spatial vs temporal vs tabbed

| Model                                 | Examples                                                      | Strength                                                                        | Why it breaks for 3 long agent streams                                                                                                                          |
| ------------------------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Spatial (tiled panes/columns)**     | tmux, Zellij, lazygit 6-panel, k9s                            | Everything visible at once; spatial memory ("git status is always bottom-left") | Width collapse. 3 vertical splits on 100 cols → 33 cols each → code/diffs wrap to mush. Long output in a short pane = a 5-line peephole onto a 500-line answer. |
| **Temporal (single interleaved log)** | docker-compose logs, foreman, kubectl logs, a chat transcript | Full terminal width per line; natural for streaming; one scrollback to search   | Without attribution, three streams interleave into unreadable chaos. Attribution is the entire engineering problem.                                             |
| **Tabbed / focus-one**                | Claude Squad (list + attach one), browser tabs                | Each agent gets full screen when focused; zero interleave noise                 | You lose concurrency awareness — the core value. Switching cost; "what is Codex doing right now?" requires a context switch.                                    |

**Verdict (INFERENCE):** Temporal-primary, with a thin spatial **ambient** layer for status only. Borrow the _block_ unit from Warp to make the temporal log navigable, and the _colored-rail_ attribution (below) to make three streams instantly tell-apart. Reserve true side-by-side panes for the one case it wins: **a focused diff** (delta-style two-column) when the operator drills into one agent's file change.

Why a block-structured log and not a raw scroll — Warp's argument, which transfers exactly to multi-agent: a `BlockList` is _"an ordered list of blocks: typed, self-contained units of content that stack vertically and scroll together"_ and crucially _"the BlockList doesn't care what's inside a block. It only needs each block's height… anything that can report a height can sit in the list next to terminal blocks"_ ([Warp block model](https://www.warp.dev/blog/block-model-behind-warps-agentic-development-environment)). That is the precise abstraction zer0 needs: a Claude turn, a Codex turn, a tool-call, a diff, and a system notice are all just **typed blocks in one stream**. Every command and its output is _"grouped into a single Block that you can copy, search, filter, bookmark… replacing the endless scroll of traditional terminals with structured, actionable output"_ ([Warp blocks docs](https://docs.warp.dev/terminal/blocks/)).

## 2. Study the masters — what specifically to copy

### lazygit — _master of dense panels + always-visible action hints_

- Six panels keep full repo state visible while you work; it _"manages to show all of this without visually overwhelming you through consistent and self-explanatory views"_ and _"makes it obvious which pane has focus and what inputs work where, lowering cognitive load"_ ([bytesizego](https://www.bytesizego.com/blog/lazygit-the-terminal-ui-that-makes-git-actually-usable)).
- **Copy:** (1) an obvious focused-panel treatment (bold/colored border on the active region only); (2) per-context keybinding hints rendered _at the edge of the focused panel_ so the user never memorizes commands; (3) the discipline that each panel is one responsibility. Jesse Duffield's own retro stresses the TUI's job is to make a complex tool _legible_, not pretty ([Lazygit 5 years on](https://jesseduffield.com/Lazygit-5-Years-On/)).
- **For zer0:** the agent roster strip = lazygit's status panel; focused-block border = lazygit's active-panel border; contextual hints = lazygit's footer.

### Zellij — _master of discoverability_

- _"When you launch Zellij, a bar at the bottom of your terminal shows you exactly which keys are available and what they do."_ The status bar is modal: enter pane mode and it _"updates to show pane-specific actions… You never need to memorize an obscure prefix-key combination because the interface tells you what is available at every moment"_ ([search synthesis]; [Zellij about](https://zellij.dev/about/)).
- Design creed: _"you shouldn't have to sacrifice simplicity for power… great experience out of the box."_
- **Copy:** a **mode-aware hint bar**. When the operator is composing → show send/route hints; when a block is focused → show fold/expand/copy/approve hints. Discoverability replaces a manual.
- Also note Zellij's **stacked panes** (collapse panes to title-only rows that expand on focus) — a direct TUI precedent for the fold pattern in §6.

### k9s — _master of semantic color as a status language_

- Color _is_ the data: _"A cyan pod is in the Running state; red indicates an error, while purple indicates the pod is being terminated"_ ([Palark](https://palark.com/blog/k9s-the-powerful-terminal-ui-for-kubernetes/)). Keybindings live in the header; number keys are namespace shortcuts; skins are fully themeable.
- **Copy:** a **fixed, learnable color→state vocabulary** for agent status (e.g. streaming / idle / awaiting-approval / error / rate-limited). Color carries state in the _ambient_ layer at a glance — but k9s also always pairs it with the literal status text (redundant encoding; see §4).
- **Caution:** k9s colorizes _short tabular cells_. Do **not** generalize that to colorizing long body prose — that is the "color everywhere" failure (§4).

### btop / htop — _master of high-resolution density in a tiny cell budget_

- btop draws _"smooth graphs"_ with _"Unicode box-drawing characters and Braille characters"_, supports true-color / 256 / 16-color fallbacks, and uses a _"darkening gradient in the process list"_ to push older/less-important rows back ([btop README](https://github.com/aristocratos/btop); [terminal.guide btop](https://www.terminal.guide/tools/system-monitor/btop/)).
- **Copy:** (1) **Braille/sparkline microcharts** for per-agent activity (tokens/sec, output cadence) in the ambient strip — high information in 1–2 cells; (2) the **darkening gradient** idea for _temporal recency_: the current/active block at full contrast, older blocks dimmed — depth without scrollbars; (3) graceful **color-depth fallback** (true-color → 256 → 16) because Windows terminals vary.

### tmux — _master of cheap, unambiguous focus indication_

- _"tmux highlights active pane's borders… via pane-active-border-style"_, and 2.1+ added `window-active-style` to _distinguish active/inactive pane backgrounds_ ([Serhat Teker](https://tech.serhatteker.com/post/2019-06/tmux-focus/)). A long-standing complaint: thin borders are _"not so visible"_, so power users also recolor the **status line** of the focused client ([tmux #2540](https://github.com/tmux/tmux/issues/2540)).
- **Copy the lesson, not the weak default:** a 1-px border is too subtle. Indicate focus with a **redundant** combo — brightened rail + bolded header + a focus sigil — not a thin line alone.

### Zellij/tmux multiplexers generally — _the negative lesson_

- Tiling is their whole identity, and it's exactly what _doesn't_ scale to three long prose streams. Borrow their **status-bar discoverability and focus model**, reject their **equal-tile layout** for the main content.

### Warp — _master of structured output (blocks) + agent/terminal fusion_

- Blocks group command+output; _"divided by horizontal lines… a visual break between different commands"_; **Compact mode** _"condenses the spacing between Blocks, enabling more content in view"_ ([Warp blocks](https://docs.warp.dev/terminal/blocks/)).
- Agent fusion: terminal blocks and rich agent-conversation blocks _"live in the same … enum, share the same SumTree, and pass through the same virtualized renderer — none of which need to know which kind of block they're handling"_ ([Warp agentic block model](https://www.warp.dev/blog/block-model-behind-warps-agentic-development-environment)). This is the literal blueprint for "agent prose, tool calls, and diffs as peers in one stream."
- **Copy:** the **block** as zer0's atomic unit; a **Compact toggle** (dense vs breathing-room); **per-block actions** (copy / collapse / approve / re-prompt) attached to the whole unit, not to fragile line selections.
- **Input position:** Warp lets input pin to the bottom; zer0 must keep a **persistent composer pinned bottom**, always focusable (kills the "input-off" bug). ([Warp input position](https://docs.warp.dev/terminal/appearance/input-position/)).

### delta + bat — _master of legible code/diffs in the terminal_

- delta side-by-side has _"line-numbers activated and syntax highlighting in both the left and right panels"_, word-level diff via Levenshtein inference, and bat's syntax themes ([delta side-by-side](https://dandavison.github.io/delta/side-by-side-view.html); [delta repo](https://github.com/dandavison/delta)).
- **Copy:** when the operator expands an agent's **file change**, render it through a delta-class viewer — syntax-highlighted, line-numbered, word-level intra-line highlight. This is the _one_ place a two-column split earns its width, and only on demand (progressive disclosure). Don't show raw unified-diff text in the chat stream; fold it to "±N lines in `file.ts`" and expand to delta-style on focus.

### fzf — _master of the peek/preview pattern_

- fzf's preview window = a live secondary panel showing the _content behind the currently selected item_ without committing to it. **Copy:** a **peek** affordance — hover/focus a folded block → preview its first N lines in place or in a side strip — the middle rung between "collapsed summary" and "fully expanded."

### neovim / LazyVim — _master of the fold gutter_

- Folding collapses ranges to a single summary line; the **foldcolumn / statuscolumn** shows fold markers and state in a dedicated left gutter, _"combining line numbers and fold indicators into a single, unified column"_ ([statuscolumn.nvim](https://github.com/wsdjeg/statuscolumn.nvim); [nvim fold docs](https://neovim.io/doc/user/fold.html)).
- **Copy:** a **left gutter column** that does double duty — agent-attribution rail **and** fold state (▸ collapsed / ▾ expanded / `+12`). One narrow column carries owner _and_ disclosure state. This is the spine of the "Anchored Gutter."

### Ink (the actual framework) — _constraints that shape the build_

- Ink runs **Flexbox via Yoga** (`flexDirection`, `justifyContent`, `alignItems`; every box is `display:flex`) ([Ink](https://github.com/vadimdemedes/ink); [studyraid](https://app.studyraid.com/en/read/11921/379933/flexbox-implementation-in-terminal)).
- `<Static>` _"permanently renders its output above everything else… useful for logs — things that are not changing after they're rendered"_ and is a **virtual-list** technique for large item counts ([Ink](https://github.com/vadimdemedes/ink)).
- **Copy / heed (INFERENCE):** render **committed history blocks via `<Static>`** (write-once, never re-rendered) and only the **live tail + composer + status strip** as dynamic Ink nodes. This is the antidote to the Windows ConPTY **corruption** bug: redrawing a huge scrollback every frame is what corrupts; `<Static>` commits finished blocks and stops touching them. Ink 3 explicitly improved `<Static>` performance for exactly this firehose case ([Ink 3](https://vadimdemedes.com/posts/ink-3)).

### Prior art — multi-agent cockpits (closest analogs)

- **Claude Code Agent Teams (split-pane):** _"each teammate gets its own pane where you can see everyone's output at once and click into a pane to interact directly"_ — requires tmux/iTerm2 ([Agent Teams docs](https://code.claude.com/docs/en/agent-teams)). Validates _"see everyone at once,"_ but inherits the width-collapse problem on a single Windows terminal.
- **Claude Squad:** a Go TUI that is a **vertical list** of sessions (↑/↓ navigate, ↵ attach), each in an isolated **git worktree**, with paused/active states; _"prioritizes task management over simultaneous multi-agent visibility"_ ([claude-squad](https://github.com/smtg-ai/claude-squad)). The negative lesson: a pure list = you _don't_ watch agents work concurrently. zer0's edge over Claude Squad is exactly the live interleaved stream.
- **NTM (Named Tmux Manager):** _"a TUI dashboard that actually tells you what your agents are doing"_ + broadcast-to-all ([NTM review](https://vibecoding.app/blog/ntm-review)). Validates the **ambient roster + broadcast** pattern.

## 3. Attributing concurrent streams — techniques compared & ranked

The single hardest sub-problem: when 2–3 streams emit at once, _who said what_ must be answerable in <200 ms, for **long** text. Options:

1. **Colored left rail / gutter (continuous vertical bar)** — a 1-col block in the agent's color running the full height of that agent's turn.
   - _Pros:_ Binds an arbitrarily long block to one owner with **zero per-line cost** (max data-ink ratio, §3a). Exploits **common region** + **proximity** — _"items within a boundary are perceived as a group"_ and a container/edge is _"a strong visual cue that can overpower… proximity or similarity"_ ([NN/G common region](https://www.nngroup.com/articles/common-region/)). Survives word-wrap: every wrapped line still sits against the rail. Scales to long output.
   - _Cons:_ costs 1 col; needs redundancy for colorblind/transparent-bg (§4).
   - **Rank: #1.** This is the spine. (lazygit/neovim gutter + Slack/Discord's colored quote-bar idiom.)

2. **Block header line (sigil + name + status + time)** at each turn's top — `▌ ◇ CLAUDE · streaming · 14:02`.
   - _Pros:_ unambiguous textual owner; anchors the block; carries status/usage. **Rank: #1-tie**, used _with_ the rail (header = the "who" in words, rail = the "who" at a glance). Common region literature: pair a boundary with a label.

3. **Per-line prefix/sigil** (`[claude] …`, docker-compose style) — Compose _"prepends the service name and color-codes each line"_ ([Docker docs](https://docs.docker.com/reference/cli/docker/compose/logs/)).
   - _Pros:_ works in a dumb pipe; owner present even on a single copied line.
   - _Cons:_ **repeats noise on every line** (low data-ink), eats horizontal width, and visually fragments a long answer. Compose itself notes interleaving _"might not tell the whole story"_ and added `--no-log-prefix` because prefixes annoy ([Dash0](https://www.dash0.com/guides/docker-compose-logs)).
   - **Rank: #3** as the _primary_ mechanism; **but** keep a faint prefix-on-wrap or first-line sigil as the **copy-safety** fallback (so a yanked snippet still says who).

4. **Side-by-side panes (one per agent)** — spatial attribution by position.
   - _Pros:_ zero temporal confusion; spatial memory.
   - _Cons:_ width collapse for long content (§1). **Rank: #4** for the main stream; viable only for short status or a focused 1-vs-1 diff.

5. **Tabs (one agent visible)** — attribution trivial because only one shown.
   - _Cons:_ kills concurrency. **Rank: last** for the main view; fine as a _drill-in_.

**Recommended stack (INFERENCE):** **rail (#1) + header (#2) as the everyday mechanism**, **faint first-line/-on-wrap sigil (#3) as copy-safety**, **delta-style split (#4) only inside an expanded diff**, **never tabs for the live view**. Three redundant channels (color rail + named header + sigil) mean attribution survives colorblindness, transparent backgrounds, monochrome copy-paste, and word-wrap simultaneously.

### 3a. Why the rail wins on data-ink

Tufte's data-ink ratio = _"the proportion of ink used to represent the data relative to the total"_; maximize it, _"erase non-data-ink"_ ([Holistics](https://www.holistics.io/blog/data-ink-ratio/)). A per-line prefix spends ink redundantly on every line to encode one fact (owner) that is constant for the whole block. A rail encodes that same fact **once, continuously**, freeing the body for content. NN/G's clutter guidance reinforces it: remove anything not carrying information ([NN/G clutter](https://www.nngroup.com/articles/clutter-charts/)).

## 4. Legibility craft in terminals

### 4a. Body text: one high-contrast color, always

- WCAG AA = **4.5:1** for body text, 3:1 for large ([WCAG 1.4.3](https://www.w3.org/WAI/WCAG21/Understanding/contrast-minimum.html); [WebAIM](https://webaim.org/articles/contrast/)). Treat 4.5:1 as the floor for agent message bodies.
- **Robustness over a TRANSPARENT or arbitrary background** (a real zer0 failure): you cannot know the bg, so you cannot guarantee a contrast ratio for _colored_ text. Two defenses (INFERENCE): (1) keep **body text near-white/foreground-default** (the terminal's own fg is contrast-guaranteed against its own bg by the user's theme), and put color **only in the rail/header/status**, where a mis-contrasted accent costs you a glanceable cue, not the readable content; (2) for any element that _must_ render over unknown bg and carry meaning, give it its **own opaque cell background** (a filled rail cell, a filled status pill) so contrast is controlled locally — like k9s status cells and tmux's `window-active-style` background, not a bare colored glyph floating on transparency.

### 4b. Color is a _channel_, not decoration — and never the _only_ channel

- WCAG 1.4.1: _"never use color alone to signify"_ meaning; ~_"1 in 8 men"_ have red-green CVD ([Princeton](https://digital.accessibility.princeton.edu/how/design/color-alone); [Silktide](https://silktide.com/accessibility-guide/fundamentals/accessible-design/designers/do-not-rely-solely-on-color/)). **Redundant encoding** (color **+** shape/icon/label/position) is the fix ([CatPAW arXiv](https://arxiv.org/pdf/2602.06792)).
- **For zer0:** every color-coded fact gets a second channel. Agent identity = color rail **+** name **+** a distinct sigil per agent (e.g. ◇ Claude, ◆ Codex, ✦ Gemini). Status = color **+** word ("streaming"/"idle"/"rate-limited") + maybe an animated spinner glyph. A red error is also the literal word and an icon.

### 4c. The "color everywhere" failure mode

- Too many colors = _"visual noise… when everything is fighting for attention, your brain works overtime just to figure out what matters"_; pros use a **small intentional palette** ([IxDF UI color](https://ixdf.org/literature/article/ui-color-palette)). The **60-30-10** rule: 60% dominant (neutral), 30% secondary, 10% accent ([hype4](https://hype4.academy/articles/design/60-30-10-rule-in-ui)). NN/G: use color to _enhance_, not to carry the whole UI ([NN/G color](https://www.nngroup.com/articles/color-enhance-design/)).
- **For zer0 (INFERENCE):** the body is ~90% neutral foreground. Each agent gets **exactly one** saturated hue, used _only_ in its rail + header + sigil — never in its prose. Three agents → three hues, chosen far apart on the wheel **and** distinguishable under deuteranopia/protanopia (avoid red↔green as the _only_ difference; lean on hue+brightness gaps, e.g. cyan / amber / magenta). Syntax highlighting inside code blocks is the one place body gets multicolor — and that's a _learned_ code palette (bat/delta themes), bounded to fenced regions.

### 4d. When to use color vs weight vs spacing vs boxing

- **Color** → identity (which agent) and state (status). Fast, pre-attentive, but fragile (bg/CVD) → always redundant.
- **Weight/brightness (bold, dim)** → _temporal & importance_ hierarchy: active block bright, settled blocks dim (btop's recency gradient). Robust on any bg.
- **Spacing (blank lines, indent)** → grouping via **proximity** (_"elements near each other are perceived as related"_ — [NN/G proximity](https://www.nngroup.com/articles/gestalt-proximity/)). One blank line between blocks, none within. Cheapest grouping; costs only vertical space.
- **Boxing/rails (borders, filled cells)** → grouping via **common region**, which _overrides_ proximity/similarity ([NN/G common region](https://www.nngroup.com/articles/common-region/)). Use the **rail** (cheap, 1 col) as the everyday container; reserve **full boxes** for things that must be unmissable (an approval prompt, an error) — a box is expensive (4 cells of border + corners) and "box everything" reintroduces clutter. Hierarchy of grouping cost: **space < dim < rail < full box.** Climb only as far as you must.

## 5. Information hierarchy — PRIMARY / AMBIENT / ON-DEMAND

Map every pixel to a tier (Tufte: maximize data-ink; progressive disclosure: defer the rest).

- **PRIMARY (the content, full contrast, center stage):** the agents' actual message bodies and final answers, in the interleaved stream. Highest contrast, neutral fg, widest measure. This is the "data"; everything else is frame.
- **AMBIENT (status, always present, low-attention, dimmed):** the **agent roster strip** — for each of the 3 agents: sigil + name + color + live state + a micro-activity sparkline + usage% (context / 5h / weekly, per the existing usage-bar work). Also the mode-aware **hint bar** (Zellij). Ambient = _peripheral vision_: present, glanceable, never competing with body text. Dim it (reduced brightness), pin it (top roster, bottom hints), and keep it 1–2 rows.
- **ON-DEMAND (folded detail, hidden until asked):** reasoning/thinking traces, full tool-call arguments, long command output, full diffs, raw logs. Collapsed to a one-line summary by default; peek → expand on focus. This is **progressive disclosure**: _"initially show only a few of the most important options… offer a larger set upon request"_, improving _"learnability, efficiency of use, and error rate"_ ([NN/G progressive disclosure](https://www.nngroup.com/articles/progressive-disclosure/)).

Grounding principles:

- **Tufte / signal-to-noise:** the message body is signal; chrome, repeated prefixes, heavy borders, decorative color are noise — minimize ([Holistics](https://www.holistics.io/blog/data-ink-ratio/), [NN/G clutter](https://www.nngroup.com/articles/clutter-charts/)).
- **Gestalt proximity + common region:** group each agent's lines tightly (no internal blank lines), separate turns with whitespace + rail color change ([NN/G proximity](https://www.nngroup.com/articles/gestalt-proximity/), [common region](https://www.nngroup.com/articles/common-region/)).
- **Visual hierarchy via contrast/brightness, not just color** (§4d).

## 6. Progressive disclosure / folding for long output

Three rungs, escalating on demand (the fzf/neovim/Zellij-stacked-pane model):

1. **Collapsed (default for any block over a threshold, e.g. >12 lines, and _always_ for reasoning/tool-args/raw logs):** one summary line + count affordance: `▸ diff: ±42 lines in reconcile.ts` or `▸ thinking (8s, 1.2k tokens)`. The gutter caret (▸/▾) shows state, neovim-foldcolumn style.
2. **Peek (on focus/hover):** preview first N lines in place or in a side strip (fzf preview) — decide whether to expand without committing the scroll.
3. **Expanded (on activate):** full content; long code/diffs render through a delta-class viewer (syntax + line numbers + word-diff). Re-collapse with the same key.

Rules (INFERENCE, grounded in progressive-disclosure + the live bugs):

- **Default-open the final answer; default-fold the process.** The operator wants conclusions; reasoning and tool plumbing are on-demand. (NN/G: disclose what's _frequently_ needed up front.)
- **Never silently truncate** — a fold always advertises what it hides (`+128 lines`). Truncation-without-affordance is the "queued-invisible / no-scroll" failure: content that exists but can't be reached.
- **Auto-fold on completion, not mid-stream.** While a block streams, show it live (operator is watching it think); once the turn settles, collapse the verbose middle and keep the summary — so the _next_ agent's turn isn't pushed off-screen. (Warp Compact mode is the manual analog.)
- **Fold preserves attribution:** a collapsed block keeps its rail color + header, so a folded Codex turn still reads as Codex.
- **One global expand/collapse + per-block toggle** (lazygit/Zellij keybinding discipline), surfaced in the hint bar.

## 7. "N feels like one" — composition patterns that fuse 3 agents into 1 super-agent

The brief's central goal. Patterns (INFERENCE, triangulated from Warp's unified BlockList + chat-transcript idioms + the operator's locked "one AI built out of three" vision):

1. **One timeline, one room.** All three agents post into a _single_ chronological stream, like one group conversation — not three windows. Shared spatial context = shared mind. (Warp proves heterogeneous blocks coexist in one list.)
2. **A single, consistent block grammar for all three.** Same header shape, same rail mechanics, same fold affordances, same status vocabulary — only the _color + name + sigil_ differ. Uniform grammar = "three voices of one system." Divergent per-agent layouts = "three bolted-on tools."
3. **A unified roster header that speaks as a team** ("3 agents · 2 streaming · 1 awaiting approval"), not three disconnected status lines. NTM's dashboard validates the single who's-doing-what surface.
4. **One composer that routes** (`@all`, `@claude`, `@codex+gemini`) — you address _the team_ from one input and choose the fan-out, rather than alt-tabbing to type into separate sessions. Broadcast-to-all is NTM's proven idiom.
5. **Cross-agent threading / reply-affinity.** When Codex responds _to_ Claude's point, show it (a quote-rail or "↳ re: Claude") so the stream reads as a _conversation between collaborators_, not parallel monologues. This is what makes three feel like one mind deliberating.
6. **Synthesis blocks.** When the team converges, emit a single distinct "team verdict" block (neutral, not owned by one agent) — the visible artifact of three becoming one. (Matches the operator's locked debate→winner / synthesis model.)
7. **Shared ambient brightness logic.** Active agent at full contrast, idle agents dim but present — they're _teammates on the bench_, visibly part of one unit (btop recency gradient applied to identity).

The anti-goal: anything that reads as "three separate terminals I happen to have open." Unity comes from **one stream + one grammar + one roster + one composer + visible cross-talk.**

| Live bug            | Root cause                                       | Design fix from this report                                                    |

| Wall-of-text        | no block structure, no folding                   | §2 Warp blocks + §6 fold-on-complete + §5 tiers                                |
| Corruption (ConPTY) | re-rendering huge scrollback every frame         | §2 Ink `<Static>` for committed blocks; only live tail dynamic                 |
| Queued-invisible    | no state for not-yet-rendered work               | §5 ambient roster shows "queued/thinking"; §6 never silently truncate          |
| No-scroll           | no scrollback/viewport model                     | §1 block list + §2 `<Static>`/alt-screen scroll region                         |
| Input-off           | composer not persistently focused                | §2 Warp input-position: composer pinned bottom, always focusable               |
| "Ghosting"          | operator's _transparent_ terminal bg (not a bug) | §4a contrast strategy for unknown bg: neutral body fg + opaque rail/pill cells |

## Design principles to adopt (ranked)

Ranked by leverage on the core problem (3 concurrent long streams → legible one-team cockpit).

1. **One interleaved block-stream, not panes or tabs.** Heterogeneous typed blocks (agent prose, tool-call, diff, system) in one chronological list. _Copy: Warp BlockList._ Kills wall-of-text + enables uniform attribution. (Foundational — everything else hangs on it.)
2. **Per-agent colored left rail + named header as the everyday attribution; redundant sigil as copy-safety.** Continuous rail = max data-ink, survives word-wrap, exploits common region. _Copy: neovim foldcolumn + lazygit active border + Slack quote-bar._
3. **Redundant encoding — color is never the only channel.** Identity = color + name + sigil; status = color + word + glyph. _Grounds: WCAG 1.4.1._ Makes the cockpit robust to colorblindness, transparent bg, and monochrome copy.
4. **Body text stays one high-contrast neutral; color lives only in rail/header/status.** Defends legibility over an unknown/transparent background; defeats "color everywhere." _Grounds: WCAG AA 4.5:1; 60-30-10._
5. **Three tiers — PRIMARY content / AMBIENT roster+hints / ON-DEMAND folds.** Message bodies at full contrast; status dimmed and pinned; process detail folded. _Grounds: Tufte data-ink, progressive disclosure. Copy: k9s status color, Zellij hint bar, btop sparklines._
6. **Progressive disclosure with a 3-rung fold (collapse → peek → expand); fold-on-complete, never silent-truncate; folds keep attribution.** _Copy: fzf preview, neovim folds, Zellij stacked panes, Warp Compact, delta for expanded diffs._ Kills the firehose without losing access.
7. **Always-visible agent roster strip (the team's pulse) + always-focused bottom composer that routes (@all / @agent).** _Copy: NTM dashboard + broadcast; Warp input position; lazygit/Zellij status bars._ Concurrency awareness + zero "input-off."
8. **Unmissable, redundant focus indication (brightened rail + bold header + sigil), not a thin border.** _Lesson from tmux's too-subtle default._
9. **Temporal recency via brightness gradient — active block bright, settled blocks dim.** Depth/recency without scrollbars; idle agents stay visibly on the team. _Copy: btop process-list darkening gradient._
10. **One consistent block grammar across all three agents; cross-agent reply-threading; team-synthesis blocks.** The "N feels like one" layer. _Grounds: operator's "one AI built of three" vision; Warp unified renderer._
11. **Render-path discipline for Ink/ConPTY: `<Static>` for committed history, dynamic nodes only for live tail + roster + composer; graceful color-depth fallback (truecolor→256→16).** Defeats corruption; portable across Windows terminals. _Copy: Ink `<Static>`, btop color fallback._
12. **Mode-aware discoverability hint bar.** The interface states available actions per context. _Copy: Zellij._ Replaces a manual; lowers cognitive load.

## Anti-patterns to avoid

1. **Three equal side-by-side panes for the live streams.** Width collapse turns code/diffs to wrapped mush — the literal "three cramped windows." Panes are for short tabular peers (k9s), not three prose+code firehoses. _(Spatial-tiling trap; the multiplexers' weakness, not their strength.)_
2. **Tabs / one-agent-at-a-time as the primary view.** Hides concurrency, defeats INV-0 and "one team." Acceptable only as a drill-in. _(Claude Squad's list-only limitation.)_
3. **Per-line `[agent]` prefixes as the _primary_ attribution.** Low data-ink, fragments long answers, eats width — Docker Compose itself shipped `--no-log-prefix` because it grates. Keep only a faint first-line/on-wrap sigil for copy-safety.
4. **Color as the _only_ attribution or status signal.** Fails ~1-in-8 men (red-green CVD), fails on transparent/unknown backgrounds, fails on monochrome copy-paste. _(Violates WCAG 1.4.1.)_
5. **Colorizing body prose / "rainbow" everywhere.** Visual noise; nothing reads as important when everything is colored. Saturated hue belongs in the rail/header/status only; multicolor is bounded to fenced code (bat/delta themes). _(Violates 60-30-10 / NN/G "enhance, don't carry.")_
6. **Colored text floating on a transparent background with no opaque cell.** Contrast becomes unknowable. Give meaningful colored elements their own filled cell; keep body in the terminal's guaranteed foreground.
7. **Unbounded streaming with no block boundaries or folding.** The wall-of-text bug; three of them at once = chaos. Every turn must be a bounded, foldable block.
8. **Silent truncation / unreachable content.** Showing only the tail with no "+N more" and no scroll = the queued-invisible / no-scroll bugs. A fold must always advertise what it hides, and scrollback must exist.
9. **Re-rendering the entire scrollback each frame.** The ConPTY corruption source. Commit finished blocks via `<Static>`; never re-touch them.
10. **A non-persistent or losable composer focus.** The input-off bug. Composer pins to the bottom, always focusable, with visible routing target.
11. **Heavy boxes around everything.** Borders are the most expensive grouping (4+ cells of chrome) and "box everything" reintroduces clutter that drowns the signal. Climb the grouping ladder (space < dim < rail < box) only as far as needed; reserve full boxes for approvals/errors.
12. **Per-agent bespoke layouts.** Divergent headers/colors/affordances per agent make it read as three bolted-on tools, killing "feel like one." One grammar, varied only by identity color+name+sigil.
13. **Thin-border-only focus indication.** tmux's well-known too-subtle default; focus must be redundant and unmissable.
14. **Decorative chrome / chartjunk** (gratuitous separators, drop-shadow-style box art, ASCII banners). Low data-ink; steals rows from content. Every glyph must carry information.
