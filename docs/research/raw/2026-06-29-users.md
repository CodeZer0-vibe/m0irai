# What developers actually want from a terminal-based multi-agent AI coding experience

Research stream: USER NEEDS / IDEAL EXPERIENCE. Independent view, no house position assumed.
Date: 2026-06-29. Author: research subagent.

## Confidence legend

- **[P]** Primary: named practitioner writeup, official vendor doc, or original study. Highest weight.
- **[C]** Community aggregation: a secondary post synthesizing Reddit/HN/forum sentiment, or a WebFetch summary of a real comment thread. Directional; individual numbers are anecdotes unless corroborated.
- **[I]** Inference: my synthesis. Explicitly marked, not a sourced claim.

## Executive summary (the one-paragraph version)

The 2026 power user does **not** pick one agent — they run two or three (Claude Code + Codex, often + Gemini/Antigravity) in **parallel terminals**, split **by task class**, and make them **review each other's diffs** ("nobody grades their own homework"). The single most repeated pain across every source is that **generation is no longer the bottleneck — review is**, so the experiences people abandon are the ones that multiply unread output ("converting typing time into reading time"). The second most repeated driver is **rate-limit walls**: Claude Code's 5-hour/weekly caps are the explicit reason people boot a second subscription. Three structural wants emerge so consistently they are effectively table stakes for a cockpit: (1) **isolation** so agents don't stomp each other, (2) **persistent + shared memory/context** across agents and sessions, and (3) **unified usage/quota visibility**. On attention, the converged ideal is "**interrupt me only when I'm not already looking, and tell me which session**." A strong contrarian undercurrent: a chunk of experienced engineers think the whole parallel-agent lifestyle is net-negative (METR measured experienced devs **19% slower** with AI on repos they knew well), so the cockpit's job is to defend review quality, not maximize agent count.

## Q1 — How power users actually combine Claude Code + Codex + Gemini today

The documented patterns are remarkably consistent. There is a real, swear-by division of labor, and it is **task-class routing + cross-review**, not "pick the best model."

**The canonical loop: Claude plans → Codex/agent implements → the other reviews.** [P]

- "A practical workflow involves: Claude plans, Codex builds, and a single markdown file connects them. Claude's job is thinking, planning, and writing the spec... then produces a clear, self-contained task document." — Beam / Towards Data Science synthesis (https://getbeam.dev/blog/claude-code-and-codex-together.html)
- The most structured version is the `claude-codex` MCP setup: "Claude plans with Opus, Codex implements or reviews, Sonnet implements or reviews, with five skills driving a structured plan → implement → review loop," routing "small changes (≤2 files, ≤30 lines) to Claude... large changes go to Codex." (https://github.com/ching-kuo/claude-codex)

**Cross-review is the load-bearing idea — repeated nearly verbatim across independent authors.** [P]

- "When Claude Code finishes an implementation, I hand the diff to Codex and ask it to tear it apart. When Codex ships something, Claude Code does the same." — XDA (https://www.xda-developers.com/use-claude-code-and-codex-together-combination-does-something-neither-can-do-alone/)
- The principle behind it: "**Nobody grades their own homework** — models reviewing their own work miss gaps they created. Cross-review catches blind spots neither tool would identify alone." (same XDA piece)
- "Don't point both tools at the same files simultaneously; they can 'stomp the other's' edits." — dev.to/rapls (https://dev.to/rapls/i-run-claude-code-and-codex-side-by-side-heres-the-division-of-labor-that-actually-works-4hkg)

**Task-class routing — who gets what work:** [P/C]

- Claude Code: "understanding existing code, explaining architecture, and making thoughtful multi-file edits"; "anything UI- or design-heavy" / "aesthetic design choices." (MindStudio https://www.mindstudio.ai/blog/claude-code-vs-codex-same-project-setup ; XDA above)
- Codex: "fast and efficient for generating boilerplate, scaffolding new features, and working through well-defined tickets"; "anything that requires sitting with a problem until it cracks"; "moves fast and trusts itself, acting akin to a senior developer." (MindStudio; XDA)
- Gemini/Antigravity: in the three-agent swarm writeup it gets "UI polish and security issues"; its consistently-cited differentiator is the **1M-token context window** — "lets it hold most of a monorepo in context at once." (dev.to/elophanto https://dev.to/elophanto/how-i-orchestrate-claude-code-codex-and-gemini-cli-as-a-swarm-4p3c ; deployhq comparison)

**The interactive-vs-automation split (a second, orthogonal axis):** [P]

- "One of them is for building and exploring, the other is for running the boring, repeatable work." Claude Code = interactive/exploratory; Codex `exec` = "repeatable, mechanical tasks fired from scripts" (version bumps, commit messages from staged diffs). — dev.to/rapls

**Config hygiene is a named, recurring practice:** separate `CLAUDE.md` (Claude) and `AGENTS.md` (Codex/Cursor); "the most common mistake is treating both agents like they should share the same instructions file." (MindStudio same-project setup). This immediately creates the **drift problem** (see Q3/Q4).

**The orchestrator role is emerging as a distinct human/tool job.** [P] The swarm author defines it as: "holds business context, translates requirements into prompts, creates isolated workspaces, monitors progress, handles failures, and notifies stakeholders" — because raw CLIs force you to "copy-paste context into every prompt, babysit terminals... manually check if they actually completed." (dev.to/elophanto)

> **[I]** This is exactly the zer0 thesis: a cockpit that _is_ the orchestrator — holds the business context + shared memory, fans work to the three native agents by task class, and runs the cross-review gate automatically — directly matches the workflow power users are hand-assembling out of tmux panes and markdown files today.

## Q2 — What developers say they want from a multi-agent terminal cockpit

The mental-model shift is the headline want.

**From pair-programming to managing a team.** [P]

- "The conductor model gives you one agent, synchronous, with your context window as a hard ceiling. The orchestrator model gives you multiple agents with their own context windows, working asynchronously while you plan and check in." — Addy Osmani (https://addyosmani.com/blog/code-agent-orchestra/)
- "3–5 focused agents consistently outperform larger teams." Benefits: parallelism (~3x throughput), specialization (each agent owns specific files), isolation (git worktrees), compound learning (shared AGENTS.md). (same)

**Concrete UI wants, straight from practitioners building/using these cockpits:**

- **Streaming that feels alive, not batch.** "aantix tried Sculptor but wants 'text build up in realtime' to feel the agent is 'alive' versus batch results." — HN "parallel coding agent lifestyle" (https://news.ycombinator.com/item?id=45489884)
- **Visual session identity.** Same commenter struggles with "color-coding Claude Code tabs red to find them visually" and wants "tab search across multiple terminals." (same HN thread)
- **Multi-output diff comparison.** "favoboa wants tools to review diffs of OLD vs NEW#1 vs NEW#2 vs NEW#3 for easy mix-and-match evaluation." Conductor author echoes it: "running multiple models on identical prompts to pick the winner." (HN 45489884; madewithlove https://madewithlove.com/blog/conductor-running-multiple-ai-coding-agents-in-parallel/)
- **Isolation by default.** Worktrees "so one agent can fix a bug while another works on authentication and a third prototypes a feature... with no risk of stepping on each other's code." (Augment Code guide; HN Zed-parallel coverage https://news.ycombinator.com/item?id=47115578)
- **Tight task contracts.** "Parallel agents only make sense if each worktree has a tight contract: scoped task, invariant tests, and a diff small enough to audit quickly." — Show HN: Superset (https://news.ycombinator.com/item?id=46368739)
- **Clean visibility of simultaneous progress** + checkpoint/rollback + testing integration. (madewithlove)

**The quality-gate scaffolding people want baked in:** [P]

- "Plan approval catches bad architecture before code exists, hooks enforce automated checks on every lifecycle event, and AGENTS.md compounds learning across sessions." — Addy Osmani. He adds the hard rule: "Never let agents modify AGENTS.md — only human review prevents degradation."

**Two features are so in-demand that the community has already built ~8–16 tools each, which is the strongest possible "they want this" signal:**

1. **Unified usage/quota tracking across agents** — caut ("monitor LLM provider usage across Codex, Claude, Gemini, Cursor, and Copilot... in one place", https://github.com/Dicklesworthstone/coding_agent_usage_tracker), tokscale (https://github.com/junhoyeo/tokscale), Quotio (https://github.com/nguyenphutrong/quotio), CodexBar (https://github.com/steipete/codexbar), QuotaMeter, Claude-Code-Usage-Monitor. Quotio's tagline is literally **"Stop juggling AI accounts."**
2. **Shared / persistent cross-agent memory** — agentmemory, the AGENTS.md↔CLAUDE.md sync tooling (symlinks, `@AGENTS.md` includes, `~/.agents/` shared dirs), and an official Anthropic feature request (see Q4).

> **[I]** zer0's two differentiating features — unified usage/quota + shared cross-agent memory — are precisely the two the community is hacking together with third-party menubar apps and symlinks. That is demand validation, not speculation.

## Q3 — What makes them abandon a tool (friction, fatigue, trust, chaos, cost)

Six abandonment drivers, ordered by how often they recur.

**1. Review/verification overload — the #1 killer.** Generation got cheap; reading didn't. [P/C]

- "The bottleneck is not how fast we can produce code but the speed at which we can review it." — HN (https://news.ycombinator.com/item?id=45110075)
- "Without [tight contracts] you're just **converting 'typing time' into 'reading time.'**" — Show HN Superset
- "Context switching between more than 2 threads of work is untenable if you want to really review code in depth." (HN 45110075)
- Simon Willison: "AI-generated code needs to be reviewed, which means **the natural bottleneck on all of this is how fast I can review the results**." (https://simonwillison.net/2025/Oct/5/parallel-coding-agents/)

**2. Permission / approval fatigue.** [P]

- Anthropic's own data: "**Claude Code users approve 93% of permission prompts.**" "Over time that leads to approval fatigue, where people stop paying close attention to what they're approving." (https://www.anthropic.com/engineering/claude-code-auto-mode)
- The two escape hatches people reach for are both bad: sandboxing ("high-maintenance: each new capability needs configuring") or `--dangerously-skip-permissions` ("unsafe in most situations"). The tool's safety mechanism becomes the thing that makes it unsafe.

**3. Merge conflicts / agents stomping each other.** [C]

- "I'd rather rewrite an entire project than try to pick through a complicated merge conflict." (HN 45110075)
- "babyshake worries parallelization creates merge hell, potentially negating speed gains." (HN 45489884)

**4. Trust failure — and it sticks.** [P]

- "A bad early experience isn't 'this tool didn't work.' It's '**this tool led me somewhere wrong and I didn't catch it**.'" — LeadDev / Honeycomb's Alyson van Hardenberg (https://leaddev.com/ai/why-engineers-lose-trust-in-ai-coding-tools)
- "When reviewing agentic generated code I can trust nothing and have to verify every assumption" — vs. a human coworker whose style you learn to trust. (HN 45489884, munk-a)
- Trust-survey numbers (secondary aggregation, treat as directional [C]): "Only 29% of developers say they trust AI output accuracy (down 11 points from 2024), 46% actively distrust it, and just 3% report high trust." (webpronews summary, surfaced via search; **UNVERIFIED against the primary survey**)

**5. Rate-limit walls + cost surprises.** (full treatment in Q5)

- "I bought two $200/month accounts. Canceled both immediately." (dev.to 500-Reddit synthesis https://dev.to/_46ea277e677b888e0cd13/claude-code-vs-codex-2026-what-500-reddit-developers-really-think-31pb)
- "Running four agents simultaneously means four times the token consumption" — unexpected billing during experimentation. (madewithlove)

**6. Unreadable output / terminal chaos.** [P]

- "When agents refactor code or generate solutions, the output lands in terminals as **a wall of raw text**: ANSI escape codes, box-drawing characters, markdown rendered as plain strings, and hundreds of lines scrolling past faster than you can read." (1DevTool https://1devtool.com/blog/terminal-reader-mode-ai-output) Broken tables = "a wall of pipes and dashes that wraps and breaks." Multiple tools (Terminal Reader Mode, visual-explainer, Overture) exist purely to fix this.

**Honorable mention — context amnesia.** "When you start a new workspace or conversation, the agent has no memory of previous work, your coding conventions, past decisions." (madewithlove) Drives both abandonment and the shared-memory demand.

## Q4 — The ideal terminal experience they describe or imply

Synthesized from the wishes above, here is the "I wish a tool would just…" composite.

**The factory/production-line model (the most concrete ideal):** Plan (precise specs + acceptance criteria) → Spawn (assign agents) → Monitor ("check progress every 5–10 minutes **without hovering**") → Verify (tests + rigorous review) → Integrate (clean merges) → Retro (update shared knowledge). — Addy Osmani.

**Specific dream features, sourced:**

- **"Improve your prompt for you"** before work starts — standardized spec templates so vague asks don't multiply errors across parallel agents. (HN 45110075) Note the psychology: "People find it a lot more palatable when the AI requires all this information than when software engineers do."
- **Agents that learn from conversations** instead of manual CLAUDE.md upkeep. "A Claude user wants agents that 'could learn from conversations' rather than requiring manual Claude.md file management." (HN 45110075)
- **Shared team/agent memory** — the strongest single demand artifact I found is an official feature request: Anthropic issue #38536 calls cross-handoff context loss **"the single biggest efficiency bottleneck for teams adopting Claude Code seriously,"** asking for a team memory pool, memory promotion (elevate a session discovery to shared memory), and context that "automatically flows to receiving engineers." Its thesis: "**Not all engineers are equally skilled at building context for AI agents — but almost everyone is effective at using agents when good context exists.**" (https://github.com/anthropics/claude-code/issues/38536)
- **Single source of truth for config** — symlink/include so CLAUDE.md and AGENTS.md can't drift. (coding-with-ai.dev https://coding-with-ai.dev/posts/sync-claude-code-codex-cursor-memory/)
- **Mix-and-match review** of competing agent outputs (OLD vs NEW#1..#3). (HN 45489884)
- **Live streaming output** so the agent "feels alive." (HN 45489884)
- **One pane, one window, no window-switching** — "no copy-pasting between windows and no context-switching... multiple AI agents working simultaneously — one writing code, another running tests, another handling git operations — all coordinated from the terminal." (search synthesis of terminal-agent comparisons; corroborated by AgentsRoom's "single window" pitch https://agentsroom.dev/ai-agent-orchestrator)

**The ideal mental posture they describe:** "You set direction, check outputs, and keep things moving." (madewithlove) The terminal becomes the **control plane** — "as agents take on more complex work, the terminal becomes the natural control plane." (search synthesis; Cline CLI 2.0 framing, DevOps.com)

## Q5 — Usage / cost / rate-limits as a driver for a second/third agent

This is one of the two strongest, best-quantified findings. Rate limits are not a footnote — they are a primary reason the multi-agent pattern exists at all.

**Claude Code's caps are the explicit trigger.** [P/C]

- "**One complex prompt burns 50-70% of your 5-hour limit. Two prompts and you're done for the week.**" — top-upvoted Reddit comment (dev.to 500-Reddit synthesis)
- Official structure: "a 5-hour rolling window plus a weekly cap on active compute hours... shared across Claude Code, Claude.ai, and Cowork." (truefoundry https://www.truefoundry.com/blog/claude-code-limits-explained)
- During the tightening, "some Max subscribers **burned weekly quotas in 1-2 days**." (productcompass https://www.productcompass.pm/p/stop-hitting-claude-code-limits, citing Anthropic's postmortem)
- A reverse-engineering finding: two cache bugs "**inflating costs by 10-20x**" silently — i.e., users hit walls partly from invisible cache misses, not just heavy use. (productcompass; QWE summary)

**The economic case for a SECOND agent is explicit and numeric.** [C — individual anecdotes, corroborated across multiple posts]

- Codex sips by comparison: "Codex uses **4x fewer tokens** for equivalent work." "Three days on Ultra High, only used 30% of weekly limit." "Never hit my limit. Coded nonstop, zero friction." (dev.to 500-Reddit synthesis) — **the specific "4x" and "67% win rate" figures trace only to this aggregation post, not a primary benchmark → UNVERIFIED.**
- Token-budget asymmetry quote: "Claude Pro... takes about 25% of the session tokens, the same task in Codex uses 60% of my week's allowance." (XDA commenter) — note this one runs the _opposite_ direction, underscoring these are workload-dependent anecdotes, not laws.
- The blunt verdict: "two $20 plans often outperforms a single Claude Code Max subscription at $100/month or higher." (dev.to synthesis)

**Cost shaped Anthropic's own roadmap** (competitive pressure is real): the May 2026 limit increases were "partly a competitive response to OpenAI's Codex product," whose "reputation for hitting walls during heavy sessions had become a recurring complaint" for Claude. (morphllm / verdent coverage via search)

**The pricing seam that makes multi-agent cheap:** "Anthropic moved programmatic Claude use... off the subscription and onto separate metered credit" (June 15, 2026) — so interactive exploration stays flat-rate, scripted automation runs metered, and "even metered it costs little per run." (dev.to/rapls)

**Auto-failover is being built as a direct answer.** Quotio offers "smart auto-failover... 'Round Robin' or 'Fill First'... ensures uninterrupted service without manual intervention" when one account hits its quota. (https://github.com/nguyenphutrong/quotio)

> **[I]** Caveat for zer0: Quotio achieves failover by **proxying/multiplexing accounts** (a ToS-gray pattern). The _legitimate_ version of this insight for zer0 is: when one agent is rate-capped or busy, the cockpit should surface "agent B/C is available — keep working" rather than silently route around quotas. The want is **continuity of momentum across caps**, expressed through unified visibility + free-agent affordance, not account laundering.

**Quantified drag from the status quo (the cost of NOT solving this):** METR's RCT found experienced open-source developers were **19% slower** when allowed to use AI tools, while _believing_ they were ~20% faster. (https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/) — see the correction note below; this is general AI overhead, not specifically rate-limit waiting.

## Q6 — Notifications / attention: interrupt me for what, leave me alone for what

A clear, converged design philosophy emerged across three independent essays + an official issue.

**The dominant principle: notify only when I'm NOT already looking.** [P]

- "Notifications trigger **only if the terminal is not in focus**... notifications serve a purpose only when you're already doing something else." Goal: "Zero annoying notifications." Implementation: `osascript` checks the frontmost app; if it's your terminal, stay silent. (wmedia https://wmedia.es/en/tips/claude-code-notify-when-done)

**Second principle: an interrupt must say WHICH session.** [P]

- "If you're running multiple Claude sessions, good luck figuring out which one wants your attention." The ideal notification answers four questions: "**which workspace, which repository, what happened, and who sent it.**" "Knowing which one finished without switching contexts is genuinely useful." (d12frosted https://www.d12frosted.io/posts/2026-01-05-claude-code-notifications)

**Third principle: distinguish "I need you NOW" from "I'm done."** [P]

- There's a real distinction between "a terminal bell when waiting for tool approval — an 'I need you right now' signal" vs "a completion bell when work is done." Two different urgencies, two different treatments. (alexop.dev https://alexop.dev/posts/claude-code-notification-hooks/) There's even an open Claude Code issue requesting a terminal BEL specifically on approval-wait (#36850).

**The async payoff that justifies notifications at all:** "notifications when tasks complete, so you can context-switch away without constantly checking the terminal." Notifications are valuable _because_ they let you leave. (d12frosted)

> **[I]** For a 3-agent cockpit this implies: (a) suppress chatter while the operator is actively reading a lane; (b) every alert is tagged by agent + repo + event-type + urgency; (c) two-tier signaling — "approval needed / blocked" (loud, pull me back) vs "lane finished" (quiet, catch on next glance). The "only when you're not looking" rule maps cleanly to the operator's transparent-terminal habit noted in zer0's own design memory.

## Surprises / contrarian findings

1. **The loudest expert view is that parallel agents make you SLOWER, not faster.** METR's randomized controlled trial: experienced devs were **19% slower** with AI on mature repos they knew well — while forecasting a 24% speedup and _still_ believing (post-hoc) they'd been 20% faster. (https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/) The perception/reality gap is the dangerous part: a cockpit that _feels_ productive can hide a real regression. **Design implication: the cockpit should protect review quality and surface real throughput, not vanity agent-count.**

2. **SOURCE-INTEGRITY CORRECTION — a widely-repeated stat is misattributed.** The dev.to "500+ Reddit developers" post claims "METR research found skilled developers took 19% longer **due to waiting on limits**." That causal framing is wrong. METR's 19% is general AI-tooling overhead (prompting, reviewing, distraction) on familiar code — **not** rate-limit waiting. Treat the dev.to post's specific figures ("4x fewer tokens", "67% win rate", the METR causal claim) as **community-claimed / UNVERIFIED**; the underlying _direction_ (Codex stretches a budget further; cross-review helps) is corroborated elsewhere, the precise numbers are not.

3. **More agents is a trap past ~3–5; the human is the ceiling.** Counter to the "run 10–20 PRs at once" marketing, practitioners cap themselves: "Context switching between more than 2 threads... is untenable if you want to really review code in depth" (HN), and Addy Osmani finds "3–5 focused agents consistently outperform larger teams." The Show HN reaction to a 10-agent terminal was open disbelief: "**How is this even a possible workflow for a person.**"

4. **People want MORE friction, not less — if the AI imposes it.** "People find it a lot more palatable when the AI requires all this information than when software engineers do." Forced specs/acceptance-criteria are welcomed from an agent but resented from a process. A cockpit can smuggle in rigor (plan approval, spec templates) that teams reject as human ceremony.

5. **The safety mechanism is the unsafe part.** Anthropic's own number: users approve **93%** of permission prompts — so the prompt is training people to rubber-stamp. The fix isn't more prompts; it's _fewer, smarter_ ones (classifier-gated auto mode). A cockpit that prompts on everything will get the same 93% reflexive-approval failure. (https://www.anthropic.com/engineering/claude-code-auto-mode)

6. **"Make it feel alive" is a genuine product requirement, not fluff.** A practitioner abandoned a batch-result tool specifically because it didn't stream: he wanted "text build up in realtime" to feel the agent is "alive." And xnx's insight on _why_ — "we anthropomorphize agents only because response time is slow enough to wait" — implies streaming cadence is doing real psychological work in keeping the operator engaged vs. walking away. (HN 45489884)

7. **The IDE can be a cage; the terminal is the escape.** Contrary to "agents belong in the IDE," a developer uninstalled Cursor for terminal Claude Code because "having it in the IDE... **you are trapped in a conversation with the LLM**." (HN 45489884) The terminal's looseness is a feature — it keeps the human in the driver's seat, not the passenger seat.

8. **Auto-failover demand is real but the popular implementation is ToS-gray.** The strongest "switch agents when capped" product (Quotio) works by proxying/multiplexing accounts. The _want_ (don't stall when one cap hits) is legitimate; the _common implementation_ is risky. zer0's clean version = unified visibility + "free agent available" affordance, not silent account routing.

9. **Gemini/Antigravity is the wobbliest leg of the tripod right now.** The June 18, 2026 forced migration from Gemini CLI to Antigravity CLI was received as "**a step backward in the short term**" for individual terminal users, and the new CLI "isn't open source." (theregister.com, developers.googleblog.com) Its one durable, repeatedly-cited advantage is the **1M-token context window**. **Implication: lean on Gemini for whole-repo context / research, not as the reliability anchor.**

## Direct implications for zer0 (inference layer — [I])

- **Cross-review is the killer feature, not an add-on.** The single most-sworn-by workflow (build with A, have B tear the diff apart) should be a first-class, one-keystroke cockpit primitive. This is zer0's Gate Topology already — the market independently arrived at the same rule.
- **The two named differentiators (shared cross-agent memory + unified usage) are exactly what the community is duct-taping together.** Ship them as native and you replace symlink-hacks and menubar apps with one cockpit. Memory want is documented at the level of an official Anthropic feature request; usage want is documented by ~8 independent tools.
- **Design the cockpit around the review bottleneck, not generation speed.** Foldable/readable output, scoped diffs, "feels-alive" streaming, ≤2 deep-review lanes, multi-output comparison. The thing that gets abandoned is whatever turns typing time into reading time.
- **Notifications: two-tier, session-tagged, suppressed-while-watching.** "I need you now (blocked/approval)" loud + pull-back; "lane done" quiet + catch-on-glance; both tagged by agent+repo+event; silent when that lane is in focus.
- **Rate-limit continuity, done cleanly.** Unified quota meters + "agent B/C free, keep moving" — momentum across caps without proxy/ToS games.
- **Respect the contrarians.** Surface honest throughput and protect review depth, so the cockpit doesn't become a machine for feeling-fast-while-being-slow (the METR trap).
