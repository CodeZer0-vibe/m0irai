# ADR-016 — Falsifying integration test for retry policy + phase events

**Status:** Proposed
**Date:** 2026-05-09
**Source:** packet-1h Phase D
**Builder:** codex (fills Decision / Alternatives / Consequences during Phase D build)

## Context

Per locked feedback `feedback_falsifying_test_mandatory_for_gates`, every analysis gate or invariant claim must ship with a falsifying test. Without one, the gate may pass vacuously. The Phase B retry policy and the Phase C idempotent phase-events activity each carry an invariant that must be falsifiably tested:

1. **Retry policy — nonRetryable codes fail fast.** A workflow whose activity throws `ApplicationFailure.create({ type: ZER0_CONTEXT_READ_FAILED, nonRetryable: true })` MUST surface failure within 2 wall-clock seconds with the activity invoked exactly once. Without the policy, the workflow would hang indefinitely (the empirical incident on 2026-05-09 — `attempt: 9` and counting).
2. **Retry policy — retryable codes retry up to maximumAttempts.** A workflow whose activity throws `ApplicationFailure.create({ type: ZER0_TEMPORAL_UNREACHABLE })` MUST be invoked exactly `maximumAttempts` times then fail.
3. **Phase events — idempotency.** A retried activity that successfully inserts on attempt 1 then throws and retries MUST result in exactly one event row with the matching `idempotency_key`.

The integration test uses `@temporalio/testing` `TestWorkflowEnvironment` with time-skip to keep CI wall-clock under 5s while exercising the full retry interval curve.

## Decision

The falsifying tests live in `tests/integration/build-packet-retry-policy.test.ts` and `tests/integration/build-packet-phase-events.test.ts`. Both use `TestWorkflowEnvironment.createTimeSkipping()` so the workflow's catalog-derived retry policy executes with real Temporal-side semantics while CI wall-clock collapses across the backoff intervals. Each `it()` block constructs its own `TestWorkflowEnvironment` and per-test temp DB, then tears them down inside `try { ... } finally { await env.teardown(); }` (matches the prior-art pattern at `tests/integration/build-packet-happy.test.ts:34-45`). Activity injection happens via `Worker.create({ activities, workflowsPath, taskQueue })` where `activities` is a `vi.fn`-mocked overlay over the production activity surface — the canonical `failureFor({ code: Zer0ErrorCode.X, message: ... })` helper from `src/shared/application-failure.ts` constructs the `ApplicationFailure` so the catalog's `retryability` field drives the `nonRetryable` flag, exactly matching how the production boundary will classify a real activity failure. The phase-events test isolates state via the `ZER0_DB_PATH` env override (G3 from the packet-1h post-mortem) — `setupDb()` writes a fresh tmp evidence DB and points the activity at it, then `cleanup()` restores the prior env value and removes the directory. Phase event sequences are asserted against the closed 7-kind happy-path enum (`packet.started`, `preflight.passed`, `phase.started`, `phase.attempt.started`, `phase.passed`, `packet.review.passed`, `packet.sealed`) read directly from the `events` table with `ORDER BY sequence`. Cancellation and exhausted-fix-loop scenarios drive `cancelSignal` and `humanInterventionResolvedSignal` via the workflow handle (re-exported as `buildPacketCancelSignal` and `humanInterventionResolvedSignal` from `src/temporal/workflows/index.ts:11-15`) and assert the `packet.cancelled` / `phase.exhausted` + `phase.escalated` rows land via the partial-UNIQUE `idx_events_idempotency` index — which collapses any duplicate emission paths the workflow may take across the multi-site cancellation handlers.

## Alternatives considered

1. **Unit test the `NON_RETRYABLE_ERROR_TYPES` catalog constant in isolation.** Trivial to write — assert that every Zer0ErrorCode whose `retryability !== "yes"` appears in the frozen list. Rejected as the sole guard: the constant correctness does not prove that the workflow's `proxyActivities({ retry: { nonRetryableErrorTypes: [...NON_RETRYABLE_ERROR_TYPES] } })` declaration actually wires it through to the Temporal scheduler, nor that activities throwing the corresponding ApplicationFailures fail-fast under the policy. The unit test passes vacuously even if the `retry:` block were silently dropped from the proxy declaration.
2. **Integration test against a real Temporal server (`temporal server start-dev`).** Highest fidelity — exercises the same scheduler binary that production will use. Rejected: 5–10× slower CI (server boot takes 3–8s per test file vs sub-second for the embedded test env), requires server lifecycle management in CI (start/stop/health-check), and adds an external binary dependency to the gate suite. The marginal fidelity over the embedded `TestWorkflowEnvironment` does not justify the operational tax for an in-process retry-policy invariant.
3. **Integration test with `TestWorkflowEnvironment.createTimeSkipping()` (chosen).** The embedded server runs in the same process; `createTimeSkipping` collapses the workflow's backoff intervals (`initialInterval: "1 second"`, `backoffCoefficient: 2`, `maximumInterval: "30 seconds"`) so the 3-attempt retry chain completes in real wall-clock under 5 seconds while the workflow's view of time still progresses through each interval. Each test owns its environment + tmp DB, so suite parallelism is safe.
4. **Manual reproducer via `zer0 build packet-99` real-E2E.** Useful for end-to-end smoke (we ran it 2026-05-09) but expensive (~10–20 min wall, requires real codex + claude dispatch, scarce weekly quota). Not suitable as a per-CI gate. Reserved for major-architecture changes only.

## Consequences

**Positive.** The retry policy and phase-event idempotency invariants are now falsifiably guarded — silently dropping `nonRetryableErrorTypes` from the proxy, regressing `maximumAttempts` away from 3, breaking the partial UNIQUE index on `(run_id, idempotency_key)`, or reordering the canonical 7-kind happy-path emission sequence each fail at least one of the six tests. This closes the empirical incident class observed 2026-05-09 (`dispatchAgent ENOENT'd at attempt: 9` with infinite retries) by making the regression detectable at gate time.

**Negative.** The tests register the workflow bundle via `workflowsPath` resolved through Windows pathname normalization (`tests/integration/build-packet-retry-policy.test.ts:221-227` and `build-packet-phase-events.test.ts:310-316`). This duplicates a workflow path normalization that already exists in `src/temporal/worker.ts:105-111`; future renames of the workflow entry path require updating both call sites. The `nonRetryable <2s + 1 attempt` assertion in isolation does not distinguish "non-retryable correctly skips retry" from "no retry policy at all" — the proof relies on its pair with the retryable-test (which forces 3 attempts) showing `maximumAttempts: 3` is active. Both tests must be kept in lock-step; deleting the retryable test silently weakens the non-retryable proof.

**Open questions.** (1) `vi.waitFor` polls in `phase-events.test.ts:69` and `:72` carry a CI flake risk if the embedded Temporal environment is starved of CPU on overloaded runners — mitigated by the explicit 10_000ms timeout on the cancel-state poll, the dispatch-call-count poll relies on the default 1000ms which may need raising. (2) `TestWorkflowEnvironment.createTimeSkipping` is a `@temporalio/testing` SDK API — major SDK upgrades may break its semantics. Pin the SDK version in `package.json` and treat its bump as a Tier-3 architectural change. (3) The `ActivityMocks` shape is duplicated across both test files; a shared `tests/integration/_helpers/activity-mocks.ts` extraction is filed as Phase E backlog (Phase D's `forbiddenFiles` blocks the cross-file refactor in this packet).
