# zer0-agent-ci — Developed Product Vision

> **Status (2026-05-29): developed vision, not current state.** This document takes the operator's remembered ideas and the six facet investigations and develops them into a grounded, buildable design. It is the engineering companion to `docs/architecture/FINAL-APP-vision.md` (the operator-facing target): same north star, same build order spine, but facet-by-facet — current state in code, the developed design, concrete mechanisms, hard parts, net-new surface, foundation dependencies, and open decisions. Every "current state" and "rests on foundation" claim is grounded against the live code, the full audit (`docs/audits/audit-zero-cli-full-audit.md`), the invariant-drift audit (`docs/audits/drift-invariant-drift.md`), and the remediation plan (`docs/plans/plan-zer0-remediation.md`).

## North star

zer0-agent-ci is a **single-operator, durable, three-agent collaborative software-creation system**: a chat surface where one human talks, and three best-in-class CLI agents — Claude (orchestrator / architect / synthesizer / reviewer), Codex (primary builder / feasibility), Gemini (world-research / grounding / cross-family reviewer) — work their complementary lanes to take an idea from a vibe prompt to shipped, reviewed, committed code. The finished product recognizes what kind of session it is (onboard an existing repo / start a greenfield one / resume / audit / debug / talk), routes ephemeral conversation through chat and durable multi-hour work through Temporal, runs a greenfield creation pipeline (intent → Q&A → research → spec → module-map → architecture → plan) whose output feeds the existing durable build-and-review loop, lets agents collaborate with shared context and mutual awareness, delegates safely under a writer-exclusive/reviewer-overlap file-ownership lock, and surfaces all of it through a live cockpit (an ink TUI now, a React drag-task-card app later). It is durable but not distributed: one embedded Temporal worker, one SQLite evidence ledger, localhost only — permanence and crash-recovery without the cluster tax.

## Core thesis: complementary specialization, NOT competition

**The corrected model: research and creation are a union of specialists synthesized into one artifact, never a tournament with a winner.** This is the single most important correction the operator made, and it has a concrete locus in code and a concrete empirical basis.

**Empirical basis — NEON SERPENT.** In our own multi-model coverage measurement, no single model exceeded **73%** coverage of the target; all three combined reached **100%** at $1.93 (recorded in `docs/architecture/FINAL-APP-vision.md:60`). The lesson is not "pick the best model" — it is "the models are complementary, and the union is the deliverable." A tournament discards the 27% only one model saw. The system already carries a fossil of the rejected tournament model: `registry.ts:87-107 dispatchWithFailover` + `DEFAULT_FAILOVER_CHAIN` (registry.ts:27) is dead code whose only caller is its own test — a failover/competition chain that was never wired. Its existence is evidence the project once flirted with the wrong model and then walked away without deleting the artifact.

**The per-model lanes (source of authority: `ROUND_TABLE.md:87-112`, verified):**

- **Claude — orchestrator / architect / synthesizer / reviewer.** Reads SPEC + PLAN before every step, never builds from memory; writes intent briefs, specs, plans, architecture decisions; runs hostile neutral-prompt reviews; never sees builder reasoning when reviewing. Claude is the only role that reads all three reasoning streams, so it is the **fixed synthesizer** — never rotated, because a rotating synthesizer re-introduces a tournament (whoever synthesizes wins ties).
- **Codex — primary builder / feasibility.** Receives a fresh context pack (objective + acceptance + owned/forbidden files, never pseudo-code); runs in an isolated worktree; answers "can this actually be built with these libraries, at this cost?" Default builder.
- **Gemini — world-research / grounding / cross-family reviewer.** The only model with live Google-Search grounding and multimodal vision; owns external/world research, fact-verification, competitor/market scan, current-API verification. Hard boundary: **Gemini writes `.md` only** — it has no write authority over any executable artifact, because a hallucinated test is worse than none (`FINAL-APP-vision.md:68-70`). Gemini's findings are proposals to verify, never verdicts.

**Two distinct collaboration shapes — and they MUST stay separate** (conflating them is what produced both the dead failover code and the gemini-banned build path):

- **SHAPE A — DIVISION OF LABOR** (specialization; non-overlapping lanes; outputs concatenated, not compared). Each model answers a *different* sub-question, so there is nothing to vote on. Gemini = "what is true in the world right now?"; Codex = "can this be built, with what?"; Claude = architecture + the merge. This is most of the research pipeline.
- **SHAPE B — CROSS-CHECK** (redundancy; *overlapping* lanes on a safety-critical question; divergence is the **signal**). The same question is posed to ≥2 models and **disagreement triggers investigation**. The canonical instance is review: builder ≠ reviewer, cross-family (SPEC-2 / invariant 2), and the GENESIS-6 union rule — *any* model's P0 = investigate; dismiss only with mechanical counter-evidence.

**The decision rule** (the gap the operator left, filled): a task is **division-of-labor** when the models answer different sub-questions (concatenate, no conflict possible); it is **cross-check** when they answer the *same* question and a false negative is costly (compare, divergence = investigate). Research phases are mostly Shape A with one Shape-B overlap — external feasibility claims both Gemini and Codex can touch (e.g., "is library X maintained AND does its API support Y" — Gemini grounds maintenance/popularity, Codex grounds the API surface; agreement raises confidence, disagreement is a flag for Claude to resolve, **not a vote**).

This thesis is the design's spine. Every facet below either implements it (research roles, collaboration awareness), enforces it (synthesis-boundary union gate, cross-family review widening), protects it (writer-exclusive locking so two builders never corrupt one lane), or surfaces it (the cockpit shows complementary contributions side-by-side, never a leaderboard).

## The 6 facets

### Facet 1 — Complementary model-strength roles + synthesis (RESEARCH-ROLES)

**Current state in code.** The complementary-union-synthesis model exists in exactly **one** place — the interactive chat path — and is structurally **banned** from the canonical durable build path.

- The role doctrine is prose-only on the durable path: `ROUND_TABLE.md:87-112` is the source-of-authority but has no code locus on Temporal.
- Roles are encoded as env *modes*, not a typed contract: `dispatch.sh` routes via `CODEX_SANDBOX` (workspace-write|read-only), `GEMINI_MODE` (build|review|synthesis), `CLAUDE_EFFORT`. The adapters encode role-as-capability: `codex.ts:113` maps build→workspace-write else read-only; `codex.ts:115-117` adds `-c web_search=live` *only* for chatMode `"research"`; `gemini.ts:156-171` maps build→auto_edit else plan/read-only. So Gemini's grounding lever and Codex's web-search lever **already exist** but are reachable only through chat's `chatMode`.
- The working synthesis lives in chat: `controller.ts:142-154 dispatchAll` fires the three agents in parallel (`Promise.allSettled`), then when `responses.length >= 2` calls `synthesizeCouncil` (`council-synthesis.ts:30-46`); Claude is the hardcoded `SYNTHESIS_AGENT` (:12) and the synthesis prompt (`:48-71`) is the actual union contract (agree / disagree-with-stronger-evidence / single-agent-flag / merged recommendation with `[claude][codex][gemini]` citations). Routing by intent: `message-router.ts` write→codex (:141), research→gemini (:155), `/council`→all-three (:106-119).
- The standalone `council.ts` CLI does the same fan-out (`:59-61`, role env `:153-158`) but has **no synthesis pass** — it writes three response files and exits (`:69-74`) and leaks full `process.env` (`:154`, audit DISPATCH-SEC-4).
- The durable Temporal build path is single-builder/single-reviewer and **excludes Gemini**: `schema.ts:21 BuilderSchema = z.enum(["claude","codex"])`; reviewer/secondaryReviewer add fresh-claude/claude-deep-audit but never Gemini. `dispatch-review.ts:119` runs ONE reviewer per call — no union, no synthesis. There is no research/spec/architecture/plan activity — `pipeline.ts:42-55` lists those phases but `:101-106` bodies only `build` and `review`; the rest are no-op transitions (drift: GENESIS-12, SPEC-14/15 ASPIRATIONAL).

**The developed design.** Honor the thesis on the durable path by keeping Shape A and Shape B separate and making **synthesis a fixed-role Temporal activity**, never workflow logic.

- **Shape A lanes** (division of labor): Gemini owns external/world research (competitor/market scan, current-API verification, Google-Search grounding, visual reference); Codex owns feasibility/implementation research (library evaluation, dependency/API precision, realistic scoping); Claude owns architecture/synthesis/orchestration. Outputs are concatenated — no conflict possible.
- **Shape B cross-check** is reserved for safety-critical same-question items (e.g. "is library X maintained and does its API support Y"). Divergence is the signal, resolved by distinguishing experiment or escalated to the operator — never a vote.
- **The synthesis contract** (generalized from chat `buildSynthesisPrompt` and hardened against the drift audit): (1) **UNION by default** — every distinct claim from every model is carried into the merged artifact; nothing dropped by majority (counters GENESIS-6 drift). (2) **ATTRIBUTION mandatory** — each merged claim cites source model AND evidence (research → URL; feasibility → library/version or file:line; architecture → spec section); an uncited claim is **rejected at the synthesis boundary** (counters SPEC-6). (3) Agreement → high confidence. (4) Same-question divergence → not merged as fact; becomes an open conflict Claude resolves with mechanical counter-evidence or escalates as a DECISION (honors GENESIS-6 "dismiss only with mechanical counter-evidence"). (5) Single-model claim → flagged "insight-or-hallucination," carried at lower confidence, and for external claims cross-checked by Gemini grounding (where the Gemini-hallucination memory and GENESIS-12 grounding meet). (6) The synthesized artifact is one document with a provenance table; it is the input to the next durable phase, so **synthesis is a Temporal activity** whose output is content-addressed (SPEC-13) and replay-stable.
- **Why Claude is the fixed synthesizer:** synthesis is the one place where seeing all three reasoning streams is required; rotating it re-introduces a tournament. Fixing it matches invariant 1 (deterministic control: the synthesizer is a worker with a fixed contract; the workflow decides *when* it runs) and keeps a single trust boundary for the "no uncited claim" gate.
- **Correcting the Gemini build-path exclusion:** Gemini stays NOT a code builder (its Windows file-write reliability is the conpty bug surface, `gemini.ts:6-13`; pragmatic implementation is Codex's lane). But it must be a first-class RESEARCH participant and a CROSS-FAMILY REVIEWER. Fix: (a) implement the research activities where Gemini's lane lives; (b) widen the REVIEWER schema to admit Gemini for cross-family review of Codex builds (codex builds → gemini reviews; claude builds → codex reviews). The BUILDER role stays codex/claude only.

**Concrete mechanisms.**
- Typed `ResearchLane` discriminated union replacing env-string role-encoding (`{model:'gemini', lane:'world-research', grounding:true} | {model:'codex', lane:'feasibility-research', webSearch:true} | {model:'claude', lane:'synthesis'}`), consumed by both `dispatch.sh` and the adapters — single source of truth over the existing levers (gemini grounding = chatMode='research' plan path `gemini.ts:164-171`; codex web search = `-c web_search=live` `codex.ts:115-117`).
- `dispatchResearchActivity({lane, question})` per lane (mirrors `dispatch-review.ts` structure), each a pure worker emitting a zod-validated `ResearchOutput{claims:{text, evidence(url|version|file:line), confidence}[]}`. Fan-out is the *workflow's* job (`Promise.all` of activity proxies — deterministic control, invariant 1), never an agent deciding who runs.
- `synthesizeResearchActivity({outputs, shape})` → `SynthesizedArtifact{mergedClaims, provenanceTable, openConflicts, flags}`, Claude as fixed synthesizer (port `council-synthesis.ts:12,48-71` into Temporal); content-addressed via `putBlob` (SPEC-13).
- **Synthesis-boundary union gate** (the union enforcement): zod refine rejecting any merged claim with empty evidence (`evidence: z.string().min(1)` per claim) and routing Shape-B divergence to `openConflicts` rather than dropping it. Falsifying test: inject a P0 raised by only Gemini → assert it survives as a flagged claim, not dropped.
- `dismissWithCounterEvidence({claim, evidenceKind:'file-exists'|'api-probe'|'grounded-search'})` — a mechanical check that must PASS before a divergent claim is dropped; otherwise escalate to operator DECISION (no Claude-say-so dismissal).
- Reviewer schema widening (small): extend `ReviewerSchema`/`SecondaryReviewerSchema` (schema.ts:22-28) to admit `gemini`; add a manifest `superRefine` asserting builder family ≠ reviewer family (closes SPEC-2 at the workflow trust boundary, not just CLI `build.ts:80`). Builder stays codex/claude only.
- Delete the dead tournament fossil (`registry.ts:87-107` + `DEFAULT_FAILOVER_CHAIN`); replace its one legitimate use (CLI-unavailable degradation, GENESIS-3) with explicit pre-dispatch availability detection + reassign-to-claude-with-logged-warning (degradation, not failover-on-error).
- Prefilter hoist (Wave-1 dependency): every research/synthesis/review dispatch runs `prefilter(contextPack(text))` before spawning (SPEC-9). Gemini world-research that quotes committed code and ships it to an external Google service is a fresh secret-exfil vector — prefilter is mandatory at this boundary specifically.

**Hard parts.**
- The synthesizer is a single model judging the other two — itself a trust-boundary risk (Claude can hallucinate a merge, drop a feasibility finding, or sycophantically agree). The union-by-default + mandatory-attribution + reject-uncited gate is the only defense, and it must be **mechanical** (schema + activity), not prompt-instruction. Deterministic invariant needed: `|mergedClaims| >= |union of evidenced input claims|`.
- Divergence-as-signal requires the *same* question posed identically, but models phrase outputs differently. Detecting that Gemini's and Codex's claims are *about the same proposition* is a semantic-equivalence problem with no clean mechanical solution. Likely answer: structure cross-check questions as explicit closed propositions up front (yes/no/value + required evidence) so equivalence is by construction.
- Gemini grounding (GENESIS-12) is load-bearing but entirely **unbuilt**, and Gemini's CLI on Windows hits the conpty teardown bug (`gemini.ts:6-13`) requiring the PowerShell wrapper + dirty-exit recovery. A flaky grounding lane silently degrades the union to claude+codex (= stale world knowledge — the exact NEON-SERPENT 73%-ceiling failure).
- Synthesis must be replay-deterministic but consumes three nondeterministic agent outputs. The activity boundary contains the nondeterminism (like `dispatch-review`), but fan-out ordering and conflict-resolution must be workflow-deterministic. If synthesis dispatches Gemini for mid-synthesis grounding, that is a nested dispatch — it must be a separate activity the workflow sequences, or replay breaks.
- Cost/latency blast radius: a spec/architecture/plan sequence becomes ~4 phases × ~4 dispatches = ~16 agent calls (each with `dispatch.sh`'s 3-retry backoff) before a line is built. Run division-of-labor lanes in parallel; reserve cross-check for genuinely safety-critical questions.

**What is net-new.** Typed `ResearchLane` contract; `dispatchResearchActivity` per lane; `synthesizeResearchActivity` (port of chat synthesis); synthesis-boundary union gate; `dismissWithCounterEvidence`; reviewer schema widening + builder≠reviewer `superRefine`; workflow-side research-phase orchestration replacing `pipeline.ts:101-106` no-ops; Gemini grounding wiring (GENESIS-12); deletion of the tournament fossil; chat→durable bridge so `/council`/research turns and the durable path share one synthesis implementation.

**What foundation it rests on.** Working prototype `council-synthesis.ts:30-71` + `controller.ts:142-154` (the proven Shape-A+synthesis to port); role-as-mode levers in `codex.ts`/`gemini.ts`; `dispatch.sh` role env + `message-router.ts` intent→lane; `dispatch-review.ts` as the structural template; `ROUND_TABLE.md:87-112` source-of-authority. **Depends on (broken/unbuilt):** Wave 1 security prefilter hoist (SPEC-9 / DISPATCH-SEC-2); the SPEC-7 malformed-output retry fix (BROKEN, on the absent Wave 4); Wave 4 workflow determinism; and the entirely-unbuilt research activities (GENESIS-12, SPEC-14/15, `pipeline.ts` stubs). This facet is mostly **net-new durable code on top of unbuilt research activities and a reviewer path with the SPEC-7 crash bug** — building synthesis on a path that cannot retry a malformed reviewer is building on sand.

**Open questions for the operator.**
- Admit Gemini as cross-family reviewer on the durable build path, given the Gemini-hallucination-pattern memory (fabricates NOT_MET on literal spec conformance)? *Recommendation: yes for code-correctness review of Codex builds, NO for spec-literal-conformance (Claude/claude-deep-audit is more reliable there).*
- Research-phase wall-clock tolerance: full-parallel lanes (higher single-host concurrency) vs serialize to bound resource use?
- When a Shape-B cross-check diverges and counter-evidence is inconclusive — always escalate to operator, or may Claude decide with a logged rationale for non-safety-critical claims? (Needs the HumanApprovalRecord mechanism either way; SPEC-10 logged-reason is currently unimplemented.)
- Is the synthesis prompt — now the highest-leverage prompt in the system — worth a Promptfoo eval gate (SPEC-12, aspirational)?
- Sequencing: thin vertical slice first (one research lane + synthesis + gemini-as-reviewer) to prove the union contract durably, or the full RECON→PLAN research pipeline at once?

### Facet 2 — Shared chat context + mutual agent awareness (COLLAB-AWARENESS)

**Current state in code.** No mutual awareness exists; chat context is in-memory + JSON, not durable-readable.
- Chat context source of truth is `transcript.json` + the in-memory `ChatSession`, NOT SQLite: `prompt-builder.ts:54` builds the window from `input.session.messages`; `session-store.ts:70-74` writes `transcript.json` as authoritative; SQLite is a best-effort mirror.
- `chat_sessions`/`chat_messages` (`schema.sql:278-302`) are **write-only**: `queries.ts:161-165` exposes inserts; there is NO `selectChatMessages` reader anywhere. The SQLite chat tables cannot feed context to a dispatched agent today.
- Council dispatch has **zero** sibling awareness: `controller.ts:156-176 runCouncilDispatches` fires all three over the *same* pre-built `input.session`; each prompt is assembled before any sibling produces output. The only place sibling outputs combine is the 4th-pass synthesis (`council-synthesis.ts:48-71`), only after all three finish, only inside Claude's prompt.
- `ChatEventBus` (`events.ts:223-248`) is in-process and ephemeral — dies with the REPL; drives UI only.
- A real durable append-only ledger ALREADY EXISTS but is unused by chat: the `events` table (`schema.sql:141-155`) with monotonic per-run `sequence`, append-only triggers (`schema.sql:251-261`), idempotency_key; `phase-events.ts:110-160` is the proven read+write pattern — but `PHASE_EVENT_KINDS` is a closed enum of build lifecycle kinds; chat is not represented.

**The developed design.** **One shared append-only event ledger (the existing `events` table) as the single source of truth, with two derived projections** — a transcript projection (what was discussed) and a live activity-registry projection (what each agent is doing now). NOT broadcast (ephemeral, lost on crash, unreplayable), NOT a standalone live-registry table (a second mutable source that drifts from the transcript).
- *Steelman of broadcast:* three CLI agents are independent OS processes spawned per turn via execa (`dispatch-service.ts:119-142`); an in-process EventBus cannot reach them, a real broadcast needs IPC/sockets and is still ephemeral (a late agent misses prior events; a crash loses awareness). The thesis requires a late/re-dispatched agent to reconstruct full context deterministically — only an append-only log gives gap-free replay.
- *Steelman of standalone registry:* it answers "who is doing what now" but not "what was discussed," duplicating transcript state → drift. Instead the registry is a **derived projection** (a fold over ledger events), optionally materialized for fast reads.
- So the ledger is authoritative; transcript and registry are folds. This also lands SPEC-5 (SQLite owns evidence, append-only) onto the chat path, which today violates it.
- **How a dispatched agent receives history:** `prompt-builder.buildPrompt` stops reading in-memory `session.messages` and instead calls `compileChatContext(db, sessionId, {window, sinceSeq})`, folding ledger events into (a) the rolling transcript window, (b) a SIBLINGS section showing each sibling's latest completed output + current status, (c) the older-context summary. A re-dispatched or newly-spawned agent reconstructs identical context — idempotent, keyed by `(sessionId, throughSeq)`.
- **Awareness representation:** a SIBLINGS block injected into every agent prompt from the registry projection — per other agent: status (idle | dispatched | streaming | completed:turnN | failed), the turn, a one-line objective, and (if completed this round) an output excerpt. For council this enables a **staged council** instead of blind-parallel: early finishers' completed events fold into still-running siblings' awareness on their next turn, and Claude's synthesis reads all three from the ledger, removing the fragile id-set branch-merge diffing (`controller.ts:271-284`).
- **Concurrency:** one chat REPL writer; agents are read-only ledger consumers. The controller is the sole writer of chat ledger events around each dispatch. WAL + busy_timeout (`schema.sql:1-2`) already tolerate the one concurrent UI reader.
- **Bridge to durable builds:** when a chat turn escalates to a pipeline build (`dispatch-one-turn.ts:105-107 → dispatchBuild`), the chat ledger records `chat.build.linked{buildRunId}`; a `chat.build.progress` projection tails `readPhaseEvents(buildRunId)` so build phase transitions surface in chat without Temporal calling back into the ephemeral EventBus. Same table, two run scopes, joined by the linked event.

**Concrete mechanisms.** Reuse the `events` table scoped `run-${sessionId}` (the existing `evidence.ts:204-206` convention) — append-only triggers + monotonic sequence + idempotency_key give replayable history for free; a **new** chat-event enum (do NOT widen the build enum — enum-widening is a recurring schema-discipline hazard) with kinds `chat.turn.started`, `chat.user.message`, `chat.agent.dispatched/.completed/.failed`, `chat.council.started/.synthesized`, `chat.build.linked/.progress`, payloads carrying turn/agent/objective/blobHash/status; `src/chat/ledger.ts` (`recordChatEvent`/`readChatEvents`, cloning `phase-events.ts:110-160`); `src/chat/projections.ts` (`foldTranscript`, `foldRegistry`→`AgentActivity[]` — pure folds, no mutable table); the missing read side (`selectChatEvents`/`selectChatMessages`); `prompt-builder.ts` rewire (source from `compileChatContext`, add `# Siblings (live)`, keep the 60k token budget + the prefilter at `:72`); controller dual-write (ephemeral bus for UI, durable ledger for awareness); opt-in staged-council; boot-time liveness reconciliation (sweep dangling 'dispatched' → compensating ledger event, append-only-safe); a context fingerprint row (mirrors `prepare-context.ts:106-110`).

**Hard parts.**
- In-round council awareness is fundamentally limited by parallelism: `controller.ts:156-176` dispatches all three on identical pre-built prompts. True "B sees A within one round" needs either staged dispatch (A→fold→B→fold→C, ~3× latency) or best-effort within-round awareness. Recommendation: parallel by default, awareness cross-turn + at synthesis; `/council --staged` for high-stakes turns.
- The foundation is broken exactly where this rests: the chat path violates single-source-of-truth (`transcript.json` authoritative, SQLite a best-effort *swallowed* mirror, `evidence.ts:69-79`, `controller.ts:325 .catch`). Reliable chat WRITES + a READ path are a prerequisite migration, not an add-on.
- Content-addressed message text means context compile resolves blobHashes; a missing/corrupt blob silently drops a turn → need a fail-loud path (and the prefilter must run on resolved text).
- Crash semantics: REPL dies after `dispatched` before `completed` → registry shows a permanently 'dispatched' agent. Need boot reconciliation via a compensating event (append-only forbids UPDATE).
- Token budget under awareness inflation: SIBLINGS competes with the 60k budget; need per-section caps + excerpting, and the trim must protect the current request.
- Schema discipline (memory): no inline `schema.sql` version bumps; any cache table / CHECK goes through migration. Reusing the existing `events` table needs **no** version bump.
- `DispatchMode` is defined twice (ARCH-6: `shared/types.ts:203` vs `chat/types.ts:14`) — the bridge crosses exactly this seam; resolve it or the bridge imports the wrong type.

**What is net-new.** `src/chat/ledger.ts`; the `ChatEventKind` enum + zod payload schema; `src/chat/projections.ts`; `compileChatContext`; read-side queries; the `prompt-builder.ts` rewire + SIBLINGS section; controller dual-write; staged-council option; bridge events + `chat.build.progress` projection; boot liveness reconciliation; context fingerprint row; migration for any optional materialized cache.

**What foundation it rests on.** The `events` table + append-only triggers (`schema.sql:141-155, 251-261`) and `recordPhaseEvent`/`readPhaseEvents` (the single load-bearing primitive reused); `putBlob` content-addressing; `ensureRunRow`; the `run-${sessionId}` scoping; WAL + busy_timeout; the prefilter (`prompt-builder.ts:72`); the chat dispatch lifecycle. **Depends on (broken):** SPEC-5 violation on the chat path (transcript.json authoritative, SQLite swallowed mirror); chat tables insert-only — both must be fixed first or `compileChatContext` reads an incomplete ledger. Also depends on resolving ARCH-6 and obeying schema-discipline + worker-restart invariants.

**Open questions for the operator.**
- Council awareness scope: parallel-with-cross-turn (fast, default) vs opt-in staged serial (full within-round, ~3× latency)? *Recommendation: parallel default + `/council --staged`.*
- Registry: ledger-fold-only (zero drift) vs also materialized cache (faster reads, second store)? *Recommendation: fold-only until measured latency demands.*
- SIBLINGS payload: full last output vs capped excerpt vs status+objective only? *Recommendation: status+objective+~800-token excerpt; full text on explicit @-reference.*
- Migration sequencing (product/UX): flip chat source-of-truth to the SQLite ledger now (correct, behavior change) vs dual-source with ledger-preferred during a transition?
- Dangling-'dispatched' liveness deadline (builds run minutes) — per-mode timeout tied to `DEFAULT_TIMEOUT_MS`?
- Cross-session awareness: within-session only (live registry), project memory handles cross-session? *Recommendation: within-session.*

### Facet 3 — Safe delegation + file-ownership concurrency (DELEGATION-CONCURRENCY)

**Current state in code.** No read/write lock and no worktree isolation today.
- The lease is per-packet only: `acquireLease` keys solely on `packetId` → `.zer0/leases/<packetId>.lock` (`lease.ts:151-153`). A duplicate-RUN guard, not a file-ownership lock — no file-set, no mode, no worktree.
- The lease is TOCTOU-broken (CONCURRENCY-1): the stale-reclaim path does an unconditional `rmSync(path,{force:true})` (`lease.ts:65`) BEFORE the `wx` exclusive create (`:68/136-141`), so two racers observing the same stale record can both end up holding a handle. Cold-start is safe (`wx` serializes); the stale-reclaim interleave is not.
- Exactly ONE shared git working tree: `dispatchAgentActivity` runs the agent in `process.cwd()` (`dispatch-agent-activity.ts:125,133,135`); `gitFilesChanged`/`commitActivity` operate on the same root — no `git worktree` anywhere in src (CONCURRENCY-4).
- `ownedFiles`/`forbiddenFiles`/`allowOverlap` exist on the Phase schema (`schema.ts:49-56,102-109`) and feed prompts/gates, but `allowOverlap` is consumed ONLY by a static manifest-time overlap validator (`validateNoOwnedFilesOverlap`, `semantic-validators.ts:95-110`) — never a runtime lock — and that validator runs at the CLI boundary, not the canonical workflow path (SPEC-2/SPEC-3 drift).
- The reviewer-overlap half is actively UNSAFE: the read-only sandbox is unenforced (DISPATCH-SEC-1, `dispatch-review.ts:175-179` — `sandbox` is dead after Zod; `CODEX_SANDBOX` defaults to workspace-write), so a "reviewer" can mutate the tree it audits.
- The lease activity dynamic-imports the CLI module (`lease.ts:11,73-74`) to evade a dep-cruiser gate (TEMPORAL-4).

**The developed design.** The operator rule — "Codex builds X ⇒ Claude cannot BUILD on X, but Claude can REVIEW X while Codex builds" — is a **multi-reader/single-writer (MRSW) lock over file-SETS, layered on git worktree isolation**, single-host single-worker.
- **Granularity:** lock per `(packetId, phase)` WRITE-CLAIM scoped to the phase's `ownedFiles` glob set — NOT per-file (multiplies TOCTOU + deadlock for no benefit) and NOT per-worktree (too coarse; would forbid the exact reviewer-overlap the operator wants). The file-SET is the natural unit because the manifest already commits to it and `validateNoOwnedFilesOverlap` already guarantees disjoint write-sets within one manifest. The lock governs CROSS-build/cross-agent contention (two `zer0 build`s, or a chat-dispatched ad-hoc Codex job vs a Temporal build) — the "custom scenarios" the operator means.
- **Lock modes:** WRITE (exclusive over its file-set) and READ (shared). Per overlapping file-set: W/W = conflict (reject); W/R = COMPATIBLE (the operator's rule — reviewer reads while builder writes); R/R = compatible. "Overlap" = non-empty intersection of expanded glob sets; disjoint sets never interact.
- **Isolation:** each WRITER gets its own `git worktree` (`.zer0/worktrees/<packetId>-<runId>`), replacing the shared-`process.cwd()` model — so two writers with disjoint file-sets build in parallel without sharing an index. READERS (reviewers) do NOT get a worktree — they review the writer's **committed SHA** in read-only mode. This is why W/R is safe: the reviewer reads an immutable commit, never the dirty index (review-after-commit already commits before review, `build-packet.ts:216-217`). **CRITICAL:** W/R safety is a lie until DISPATCH-SEC-1 is fixed — a reviewer that can write defeats the read-lock's premise. The read-lock and the read-only-sandbox enforcement **must ship together** or the design is security theater.
- **Lock state location:** a singleton `LockManagerWorkflow` (workflowId `zer0-lock-manager`) holds the authoritative lock table and grants/revokes via signals + queries — because Temporal owns state (SPEC-5), giving durable, replay-safe, crash-recoverable locks without a TOCTOU file race. The file-backed lease is **demoted** to what it actually is — a coarse per-packet duplicate-run guard at the CLI boundary — CAS-fixed (CONCURRENCY-1) but NOT the file-set lock. This separates "is this packet already building?" (lease, CLI) from "who may write/read this file-set now?" (LockManagerWorkflow, durable).
- **Acquisition protocol:** before its first write phase a build signals `requestLock({holderRunId, fileSet, mode:WRITE})`; the manager grants iff no conflicting holder, else the requester `await`s a `lockGranted` signal (Temporal-native blocking, replay-safe, no busy-wait). A reviewer signals `requestLock({mode:READ})`, granted immediately if no WRITER conflict — and since W/R is compatible, a reviewer of a set someone is WRITING is still granted (that IS the operator rule). Released on phase exit, force-released on completion/cancel in a `finally` (mirroring `build-packet.ts:142`). Heartbeat/TTL on holder runId (reuse PID-liveness from `lease.ts:122-134`) reclaims locks from dead holders.
- **Conflict detection — two layers.** STATIC (manifest-time, exists): `validateNoOwnedFilesOverlap` + a new cross-manifest/cross-run glob-intersection check, moved INTO `preflightActivity` (closes SPEC-3 "wrong place" drift). DYNAMIC (runtime): the LockManager compatibility check at grant time, plus a post-build OWNED-FILES gate diffing `gitFilesChanged()` against declared `ownedFiles` — FAIL if a writer touched a file outside its claim (defends writer-exclusivity against an agent ignoring its brief; `forbiddenFiles` feeds this).

**Concrete mechanisms.** `src/temporal/workflows/lock-manager.ts` (singleton; lock table, `requestLock`/`releaseLock`/`reclaimExpired` signals, `lockTable` query, parked-requester grant via `lockGranted`); `src/temporal/lock/compat.ts` (pure replay-safe: `conflict = intersect≠∅ AND a.mode===WRITE AND b.mode===WRITE` — W/R and R/R compatible); `src/temporal/activities/worktree.ts` (`prepareWorktreeActivity`/`teardownWorktreeActivity` wrapping `git worktree add --detach`/`remove --force`); modify `dispatch-agent-activity.ts:125,133,135` to take an explicit `cwd` (worktree path) threaded from `build-packet.ts`; CAS-fix `lease.ts:64-68` (`wx`-create FIRST; only delete+retry if the on-disk record byte-equals the observed stale record); move `validateNoOwnedFilesOverlap` + cross-run intersection into `preflightActivity`; post-build `OWNED_FILES_VIOLATION` gate in `build-packet.ts`; co-fix `dispatch-review.ts defaultDispatch` env (`CODEX_SANDBOX=read-only`, `extendEnv:false`); LockManager `reclaimExpired()` reusing `isPidAlive`+TTL.

**Hard parts.**
- **Two contention domains.** In-process Temporal builds coordinate through the singleton LockManagerWorkflow, but a chat-dispatched ad-hoc Codex job (the bridge path, NOT Temporal) shares the SAME git tree and must ALSO take a lock — yet it has no workflow to signal. Bridging chat→lock requires the chat dispatcher to acquire via a Temporal client signal (or the demoted file-lease) before it writes. The operator's "custom scenarios" live exactly here.
- git worktree + better-sqlite3 + Windows: multiple worktrees share one `.git/objects` and ref-lock discipline; concurrent `git worktree add`/`commit` can serialize on git's ref locks; the shared `evidence.db` is opened by concurrent writers (`dispatch-agent-activity.ts:256-259`). Real concurrency load test required (CONCURRENCY-4 hazard untested).
- W/R safety REQUIRES an immutable read target — only safe because review happens after commit (`build-packet.ts:216`). If any future path lets a reviewer read the dirty index, the read-lock is a correctness lie. Encode the invariant, don't assume it.
- The read-lock is worthless while DISPATCH-SEC-1 is open — a 'READ' holder that can physically WRITE is *strictly worse* than today because it advertises safety. One atomic change.
- Lock-table durability vs the demoted lease: two stores risk re-introducing the "right idea, wrong place" drift unless the boundary (lease = duplicate-run-at-CLI; LockManagerWorkflow = file-set-at-runtime) is contract-fixed.
- Deadlock/ordering: A-then-B vs B-then-A can deadlock at the LockManager. Mitigation: acquire ALL of a build's write-claims atomically at preflight (the manifest declares every phase's ownedFiles up front) — but that reduces overlap parallelism. Real tradeoff.

**What is net-new.** `lock-manager.ts`; `lock/compat.ts`; `activities/worktree.ts`; explicit-`cwd` thread through `dispatch-agent-activity.ts`/`build-packet.ts`; atomic write-claim + reviewer READ + post-build `OWNED_FILES_VIOLATION` gate; lease CAS fix + purpose demotion; `validateNoOwnedFilesOverlap` + cross-run intersection moved to `preflightActivity`; DISPATCH-SEC-1 co-fix; chat→lock bridge acquisition; new error codes `OWNED_FILES_VIOLATION` (non-retryable) + `LOCK_CONFLICT` (parked) with falsifying tests.
