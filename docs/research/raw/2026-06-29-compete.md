# Competitive Teardown — Multi-Agent Orchestration + Terminal Diff/Review UIs

Independent research stream for **zer0 chat** (Windows TUI cockpit running Claude + Codex + Gemini/agy as one team, shared cross-agent memory, unified usage tracking). Brief: find the white space and the diff/review interaction model to copy.

**Sourcing note.** All claims below carry a URL + verbatim quote where I could get one. Dates reflect what sources state (current month per the search tool: June 2026). `INFERENCE` marks my own reasoning, not a sourced fact. No access-blocks hit — GitHub READMEs, vendor docs, and vendor blogs all fetched cleanly. The web is saturated with SEO/affiliate "review" blogs of low trust; I down-weighted those and leaned on primary vendor docs + GitHub READMEs for load-bearing facts (platform support, memory model, review flow).

**Bottom line up front.** The parallel-agent-orchestration category is real, crowded, and **almost entirely Mac-first**. Exactly one serious competitor is Windows-native (Warp), and it is a heavyweight cloud-tied terminal *replacement*, not a focused cockpit. Exactly one tool pools memory across heterogeneous agents (Warp again, and it's cloud/Drive-bound). The dominant review model for *parallel* agents is **post-hoc diff review**, not per-action gating — and the evidence says that is also what scales. zer0's three core bets (Windows-native terminal, pooled local shared brain, post-hoc Ctrl+R review with per-action deferred) land squarely in the white space.

# Part A — Orchestration / parallel-agent tools

## Conductor (Melty Labs)

- **Platform: Mac-only.** Homepage headline: *"Run parallel coding agents on your Mac."* No Windows mention anywhere on the landing page. ([conductor.build](https://www.conductor.build/))
- **Display / concurrency:** native Mac app, the original "agentic parallel runner." *"You launch several Claude Code or Codex agents at once, each working inside an isolated workspace, and Conductor gives you a single place to watch them, review their diffs, and ship the changes."* Each workspace is *"its own git worktree on its own branch. Conductor only copies files git is tracking, so node_modules and .env don't duplicate."* ([madewithlove teardown](https://madewithlove.com/blog/conductor-running-multiple-ai-coding-agents-in-parallel/))
- **Review/merge:** *"See at a glance what they're working on, then review and merge their changes."* ([conductor.build](https://www.conductor.build/)) Mechanism is post-hoc per-workspace diff → merge. Full trace logs per thread for replay/audit (madewithlove).
- **Agents:** *"Create parallel Claude Code, Codex, and Cursor agents in isolated workspaces."* No Gemini. ([conductor.build](https://www.conductor.build/))
- **Shared memory:** none surfaced; the model is isolation, not pooling.
- **Maturity:** *"As of June 2026 it is a San Francisco company of roughly six people with $22M in Series A capital… Cursor support landed in v0.63.0 (June 2026) alongside a new Dispatcher feature."* ([CodePick](https://codepick.dev/en/guides/conductor-build-intro/))
- **Biggest weakness:** **Mac-only**, and worktree-based isolation means every agent shares the host environment (dependency reinstalls, port collisions) and there is no cross-agent memory. It watches agents; it does not make them one team.

## Claude Code native "Agent Teams" (Anthropic) — the incumbent to beat on Windows

This is the most important comparison: it is the *first-party* version of zer0's concept, and it is **broken on Windows-native terminals**.

- **Concept:** *"One session acts as the team lead, coordinating work, assigning tasks, and synthesizing results. Teammates work independently, each in its own context window, and communicate directly with each other."* ([Claude Code docs](https://code.claude.com/docs/en/agent-teams))
- **Display:** *"In split-pane mode, each teammate gets its own pane… requiring tmux or iTerm2."* ([Claude Code docs](https://code.claude.com/docs/en/agent-teams))
- **Windows reality — the killer fact:** *"Split panes require tmux or iTerm2; the default in-process mode works in any terminal. However, split-pane mode isn't supported in VS Code's integrated terminal, Windows Terminal, or Ghostty."* On Windows *"visualizing this properly requires WSL2 and tmux."* ([search synthesis incl. ardalis.com WSL2+tmux guide](https://ardalis.com/setting-up-claude-code-agent-teams-with-wsl2-and-tmux-on-windows/))
- **Known defect:** *"Agent teams created via Task tool with team_name spawn new tmux panes by splitting the current window, which breaks the user's existing layout and causes command corruption when multiple agents start simultaneously."* ([anthropics/claude-code#23615](https://github.com/anthropics/claude-code/issues/23615))
- **Shared memory:** teammates have *separate* context windows + message-passing; no pooled brain. Coordination is conversational, not a shared store.
- **Biggest weakness:** **the visual model is tmux/iTerm2, i.e. Mac/Linux.** On Windows it degrades to WSL2+tmux with layout-corruption bugs. `INFERENCE:` this is the single clearest validation of zer0's thesis — Anthropic's own multi-agent UX does not run natively on Windows Terminal, and a purpose-built Windows TUI that renders independent agent lanes without tmux is a real, unclaimed slot. (Third parties — e.g. [cmux](https://cmux.com/blog/cmux-claude-teams) — are already racing to render Claude teammates "as native panes," confirming the gap is felt.)

## Claude Squad (smtg-ai)

- **Platform:** TUI; **requires tmux + gh.** *"tmux to create isolated terminal sessions for each agent."* README documents Homebrew (macOS) and a Linux bash installer; **no native Windows path, WSL not mentioned.** ([github.com/smtg-ai/claude-squad](https://github.com/smtg-ai/claude-squad))
- **Display:** *"Manage instances and tasks in one terminal window"*, list-style TUI, `↑/j ↓/k` navigation. ([README](https://github.com/smtg-ai/claude-squad))
- **Review/diff:** *"tab — Switch between preview tab and diff tab"*, `shift-↑/↓` scroll in diff; *"Review changes before applying them, checkout changes before pushing them."* Post-hoc, per-instance. ([README](https://github.com/smtg-ai/claude-squad))
- **Concurrency:** *"Each task gets its own isolated git workspace, so no conflicts"* via git worktrees. ([README](https://github.com/smtg-ai/claude-squad))
- **Agents:** *"manages multiple Claude Code, Codex, Gemini (and other local agents including Aider)."* ([README](https://github.com/smtg-ai/claude-squad)) — same three families as zer0.
- **Shared memory:** none; *"No shared context mechanism is described"* — isolation is the whole design.
- **Biggest weakness:** **tmux dependency = not Windows-native**, and it is a session *manager* (reduces sprawl) with zero cross-agent intelligence. It is the closest open-source analog to zer0's surface, and it stops exactly where zer0 starts (shared brain, unified usage, Windows-native render).

## Vibe Kanban (BloopAI)

- **Platform:** web UI launched locally; README shows *"Build from source (macOS)"* and no explicit Windows support. **The project is sunsetting** (README banner links a sunset announcement). ([github.com/BloopAI/vibe-kanban](https://github.com/BloopAI/vibe-kanban))
- **Display/review:** kanban board metaphor. *"Plan with kanban issues"*; *"Review diffs and leave inline comments — send feedback directly to the agent without leaving the UI"*; *"Preview your app — built-in browser with devtools."* ([README](https://github.com/BloopAI/vibe-kanban))
- **Merge:** *"Create pull requests and merge — open PRs with AI-generated descriptions, review on GitHub, and merge."* ([README](https://github.com/BloopAI/vibe-kanban))
- **Concurrency:** each task in its own git worktree; broad agent support (Claude Code, Gemini CLI, Cursor CLI, Codex, Copilot, Qwen, OpenCode, Amp). ([github.com/BloopAI/vibe-kanban](https://github.com/BloopAI/vibe-kanban))
- **Shared memory:** none surfaced.
- **Biggest weakness:** **it's a browser app, it's sunsetting, and the "inline comments → agent" is its one genuinely good idea** (mid-task redirect via review comments). Worth copying that one interaction; the kanban shell itself is heavyweight for a single operator.

## Crystal → Nimbalyst (Stravu)

- **Platform:** Electron desktop (cross-platform-capable). **Crystal is deprecated** (Feb 2026), succeeded by **Nimbalyst**. ([github.com/stravu/crystal](https://github.com/stravu/crystal); [nimbalyst.com/crystal](https://nimbalyst.com/crystal/))
- **Model:** *"Run multiple Codex and Claude Code AI sessions in parallel git worktrees. Test, compare approaches & manage AI-assisted development workflows in one desktop app."* Each session in its own worktree. ([github.com/stravu/crystal](https://github.com/stravu/crystal))
- **Shared memory:** none surfaced; worktree isolation.
- **Biggest weakness:** Electron desktop (heavy), and the category is being commoditized — *Claude Code's own desktop app now ships "automatic Git worktree isolation"* per-session ([miraflow](https://miraflow.ai/blog/claude-code-desktop-redesign-parallel-sessions-routines-workspace-guide)), which is exactly the gap Crystal/Nimbalyst filled. `INFERENCE:` worktree-isolation-as-a-product is being absorbed by the agents themselves; differentiation has to be *above* isolation (coordination, memory, review UX).

## Superset (superset-sh, YC S26)

- **Platform: macOS only.** README, verbatim: *"OS: macOS (Windows/Linux untested)."* ([github.com/superset-sh/superset](https://github.com/superset-sh/superset))
- **Display/review:** *"Built-in Diff Viewer: Inspect and edit agent changes without leaving the app"*; *"Review and edit changes quickly with the built-in diff viewer and editor."* ([README](https://github.com/superset-sh/superset))
- **Concurrency:** *"Worktree Isolation: Each task gets its own branch and working directory"*; goal of *"100+ agents in parallel"* (currently 5–7 reliably per [Founderland](https://www.founderland.ai/articles/superset-launches-ide-to-orchestrate-100-ai-coding-agents-in-mpz8db7u)).
- **Agents:** *"Superset works with any CLI-based coding agent"* — Claude Code, Cursor Agent, Copilot, Codex CLI, Gemini CLI, Amp, Droid, OpenCode, Pi, etc. ([README](https://github.com/superset-sh/superset))
- **Shared memory:** README does not describe cross-agent memory; isolation-first.
- **Biggest weakness:** **macOS-only by their own admission**, and the "100 agents" framing optimizes for *fan-out volume* over coordination — more swarm than team. No shared brain.

## Warp — Agents / Oz / Warp Drive (the one real Windows competitor)

This is the most direct threat to zer0 on the two axes zer0 claims (Windows-native + pooled memory).

- **Platform: Windows-native, GA.** Download offers `.exe` for *"Windows 11/10 x64"* and *"Windows 11/10 ARM64"* plus `winget install Warp.Warp`. ([warp.dev Oz/agents pages](https://www.warp.dev/blog/multi-harness-cloud-agent-orchestration)) Launch post: *"Warp, the intelligent terminal, now available on Windows!"* ([warp.dev blog](https://www.warp.dev/blog/launching-warp-on-windows)); written in Rust, GPU-rendered.
- **Single-pane orchestration:** *"Oz provides the ability to launch, track, govern, and steer any of these agents in one unified control plane… It's a single pane of glass for all your cloud agents."* ([multi-harness blog](https://www.warp.dev/blog/multi-harness-cloud-agent-orchestration))
- **Pooled cross-agent memory — the standout:** *"Cross-harness Agent Memory: the only cross-harness memory system that helps agents remember what works for your team across every session, repo, and project."* And: *"Agent Memory is also inherently multi-harness, so it can form memories from Claude Code and Codex sessions."* ([multi-harness blog](https://www.warp.dev/blog/multi-harness-cloud-agent-orchestration))
- **Harnesses:** *"Oz now supports running Claude Code and Codex as agent harnesses in addition to Warp Agent."* Gemini CLI is supported in the *terminal* but not explicitly in *Oz* orchestration. ([multi-harness blog](https://www.warp.dev/blog/multi-harness-cloud-agent-orchestration))
- **Subagents:** *"Warp Agent… is the only harness that can orchestrate subagents, able to spawn cross-harness subagents (for example, a Warp Agent parent dispatching a Claude Code or Codex child)."* ([warp.dev/agents](https://www.warp.dev/agents))
- **Review model:** not clearly per-action; Oz emphasizes "steer" + management interface across subagents (post-hoc/on-the-loop). No per-action approval prose found.
- **Biggest weakness (and zer0's opening):** Warp is a **full terminal replacement + cloud platform (Oz)**, not a focused cockpit. The memory and orchestration are **cloud/Warp-Drive-bound** — your team's context lives in Warp's cloud, which is exactly the privacy/lock-in posture an operator running local subscription CLIs may reject. `INFERENCE:` zer0's wedge vs Warp is (a) *local* shared brain (event-sourced SQLite, no cloud), (b) not asking the user to abandon their terminal, (c) three *co-equal* subscription agents incl. Gemini/agy, where Warp centers its own Warp Agent and treats Gemini as second-class in Oz.

## Aider

- **Platform:** terminal, Python (pipx); **Windows-compatible** (docs reference `.venv\Scripts\activate`). ([aider.chat](https://aider.chat/); [deployhq guide](https://www.deployhq.com/guides/aider))
- **Review model — distinct philosophy:** *git-history-as-review.* *"By default, it automatically commits every change the AI makes, giving you a clean history of AI-assisted edits that you can review, revert, or squash."* `/diff` shows working-tree diff vs last commit; `/undo` reverts the last change. ([deployhq guide](https://www.deployhq.com/guides/aider)) No pre-apply gating — it applies, commits, and you review/undo after.
- **Architect mode:** *"a strong reasoning model plans the change, and a fast/cheap editor model emits the actual file edits in Aider's diff format."* ([deployhq guide](https://www.deployhq.com/guides/aider)) — a two-model split, not multi-agent teamwork.
- **Concurrency / shared memory:** single-agent pair-programmer; no parallel agents, no shared brain. Multi-agent only if wrapped by Claude Squad/Vibe Kanban et al.
- **Biggest weakness:** **single-agent**; auto-commit-then-review is fast but trades away pre-apply control. Its value to zer0 is the *philosophy lesson*: "apply + atomic commit + cheap undo" beats heavyweight gating for trusted flows.

## Cursor (Agents / Composer / Background Agents)

- **Platform:** cross-platform Electron IDE (Windows OK). Not a terminal cockpit.
- **Parallel agents:** *"run several agents in parallel on different tasks… each with its own working set, model, and approval policy"*; *"up to eight agents in parallel on a single prompt using git worktrees or remote machines."* ([digitalapplied Cursor 3 deep dive](https://www.digitalapplied.com/blog/cursor-3-deep-dive-agents-composer-review-2026); [cursor.com/changelog/2-0](https://cursor.com/changelog/2-0))
- **Review/diff:** *"Multi-file edits stage as a reviewable diff with explicit accept-per-file controls."* Background agents land work *"as a pull request."* ([digitalapplied](https://www.digitalapplied.com/blog/cursor-3-deep-dive-agents-composer-review-2026))
- **Shared memory:** per-agent isolated checkouts; no pooled cross-agent memory described.
- **Biggest weakness:** **it's an IDE, not a terminal**, and the multi-agent story is fan-out-on-one-prompt (race N attempts, pick a winner) rather than a *coordinated team with division of labor*. Accept-per-file is a good, copyable review primitive.

## Zed (Agent Panel / Parallel Agents / ACP)

Most relevant for zer0's transport: Zed drives external agents over **ACP** (the same protocol zer0 adopted as default).

- **Platform:** native Rust editor, cross-platform.
- **External agents over ACP:** *"Each thread can use a different agent, so you can run Zed's built-in agent in one thread and an External Agent like Claude Code or Codex in another."* Caveat: *"Some agents (such as Cursor and Gemini CLI) are not currently supported."* ([zed.dev/docs/ai/parallel-agents](https://zed.dev/docs/ai/parallel-agents))
- **Display:** *"The sidebar shows your threads grouped by project… Threads appear below with their title, status indicator, and which agent is running them."* *"Each thread works independently with its own agent, context window, and conversation history."* ([parallel-agents docs](https://zed.dev/docs/ai/parallel-agents))
- **Diff review — best-in-class agent model:** *"click the `Review Changes` button (shift-ctrl-r), which opens a special multi-buffer tab with all changes. You can accept or reject each individual change hunk, or the whole set of changes made by the agent."* Plus inline mode: *"Edit diffs can also appear inline in individual files with the same keep/reject hunk controls."* ([zed.dev/docs/ai/agent-panel](https://zed.dev/docs/ai/agent-panel))
- **Shared memory:** explicitly **none** — *"Each thread works independently with its own… context window, and conversation history."* ([parallel-agents docs](https://zed.dev/docs/ai/parallel-agents))
- **Biggest weakness:** **no shared memory across threads** and Gemini CLI not supported over ACP yet (mirrors zer0's agy/ACP blocker — antigravity-cli #31). But Zed's **multi-buffer keep/reject-hunk review pane is the single best agent-diff UX I found** and is the model to copy (see Part B + final section).

## Sculptor (Imbue)

- **Platform:** *"Sculptor is now available on Mac (Apple Silicon) and Linux, with Mac (Intel) and Windows support on the way."* → **Windows not yet shipped.** ([imbue.com/sculptor-announce](https://imbue.com/sculptor-announce/))
- **Isolation model — containers, not worktrees:** *"Every agent runs in its own container… Unlike git worktrees—which share your local environment and require reinstalling dependencies for every agent—Sculptor containers keep your machine safe."* ([sculptor-announce](https://imbue.com/sculptor-announce/))
- **Review via Pairing Mode:** *"With one click, Sculptor brings an agent's work from its container into your local repo, keeping your files and git state synced so you can collaborate directly from your IDE. Test the agent's work instantly… and commit changes you like."* ([sculptor-announce](https://imbue.com/sculptor-announce/))
- **Context persistence:** *"Sculptor saves every agent session with its plans, chats, tool calls, and code changes all intact. You can reopen a past session anytime to pick up where you left off."* ([sculptor-announce](https://imbue.com/sculptor-announce/)) — per-session persistence, **not** cross-agent pooling.
- **Biggest weakness:** **not on Windows yet**, and Docker-container isolation is heavier than worktrees (great for safety, costly for a Windows operator on subscription CLIs). Per-session save ≠ shared brain.

## Devin / Devin Desktop (Cognition)

- **Platform:** cloud-first; new **Devin Desktop** as local "Agent Command Center."
- **Display:** *"The Agent Command Center is a Kanban-style interface for managing multiple agents simultaneously."* ([the-agent-report](https://the-agent-report.com/2026/06/cognition-devin-desktop-agent-orchestration/); [fixedlabs review](https://www.fixedlabs.ai/blog/devin-desktop-review))
- **Concurrency:** *"Up to 10 concurrent Devin sessions… each in its own sandbox, executing in parallel,"* delivering *"10+ tickets simultaneously for review."* Subagents report back to a main agent. ([buildfastwithai](https://www.buildfastwithai.com/ai-tools/devin))
- **Cost model:** billed in **ACUs (Agentic Compute Units)** — VM time + inference + bandwidth. ([buildfastwithai](https://www.buildfastwithai.com/ai-tools/devin)) Opaque/consumption pricing, the opposite of zer0's flat-subscription posture.
- **Shared memory:** improved *"context retention"* claimed; no pooled cross-agent brain detailed.
- **Biggest weakness:** **cloud + metered ACU pricing + ticket/PR async workflow.** It's an autonomous-employee product, not an operator's interactive cockpit. Expensive and opaque vs. subscription-flat.

## Cline + Roo Code (VS Code agents) — the per-action-gating reference

- **Platform:** VS Code/JetBrains extensions (Windows OK). Single-agent (Cline now also SDK/CLI).
- **Cline — strict per-action gating:** *"Plan reading and reasoning, and Act executing with per-step approval… Every file edit and terminal command requires your approval."* Granular **auto-approve** whitelists (reads/writes/terminal/browser/MCP) + a **YOLO mode** that *"removes all per-action confirmations."* ([cline docs auto-approve](https://docs.cline.bot/features/auto-approve))
- **Checkpoints:** *"Cline maintains a shadow Git repository… and commits the file state after each tool use,"* with Restore Files / Restore Task / Restore Both. ([search synthesis](https://www.deployhq.com/guides/cline)) — strong undo primitive.
- **Roo Code — more autonomous, better diff:** *"a more polished 'Diff' view… side-by-side diff that is much easier to review than Cline's inline blocks."* But **Roo Code shut down May 15, 2026; repo archived.** ([qodo comparison](https://www.qodo.ai/blog/roo-code-vs-cline/))
- **Framing:** *"Cline is for control, Roo Code is for speed."* ([qodo](https://www.qodo.ai/blog/roo-code-vs-cline/))
- **Shared memory:** none (single agent).
- **Biggest weakness:** **single-agent + per-action approval fatigue** (the reason YOLO mode and granular auto-approve exist). `INFERENCE:` Cline is the canonical proof that pure per-action gating doesn't survive contact with real volume — users immediately reach for auto-approve. Validates zer0's choice to keep agents on AUTO and review post-hoc, with per-action as an *opt-in seam* (the dormant `PermissionDecider`), not the default.

## OpenHands

- **Platform:** Docker-first; runs on Windows via Docker Desktop, plus a native-server option. *"OpenHands agents can either use the local machine as their workspace, or run inside ephemeral workspaces (e.g. in Docker or Kubernetes)."* Windows setup via `README.windows.md`. ([github.com/OpenHands/openhands](https://github.com/OpenHands/openhands))
- **Security posture:** *"For headless/automated execution, Docker should always be used… more secure than native execution on your filesystem."*
- **Shared memory:** multi-agent SDK exists; no operator-facing pooled-brain cockpit.
- **Biggest weakness:** **Docker dependency + research-platform ergonomics.** Powerful SDK, not a polished single-operator Windows cockpit. Windows is supported but via Docker, not native TUI.

# Part B — Diff / review TUIs (the interaction model library)

## lazygit (the keyboard gold standard)

The richest TUI review model; copy its keymap wholesale.

- **Hunk + line staging:** *"press Enter on a file to enter the diff view, then press Space on any hunk to stage just that section… press space on any line in the diff view to stage just that line, press v to enter visual mode and select a range, or press a to select the entire hunk."* ([lazygit guide](https://viadreams.cc/en/blog/lazygit-guide/); [keybindings](https://github.com/jesseduffield/lazygit/blob/master/docs/keybindings/Keybindings_en.md))
- **Navigation:** *"j/k or arrow keys move through items. Enter dives into the selected item… and Esc goes back up."* Toggle line-vs-hunk granularity. ([lazygit guide](https://viadreams.cc/en/blog/lazygit-guide/))
- **Why it feels best:** one consistent verb set (`j/k` move, `Enter` dive, `Esc` up, `Space` stage, `v` range, `a` hunk, `Tab` switch panel) across every panel, and *progressive disclosure* — files → hunks → lines without leaving the keyboard. This is the canonical terminal review grammar.

## gitui

- **Rust, faster, lighter:** *"2x faster than lazygit with 1/15th the memory usage"* on huge repos; `Enter` stage/unstage, `s` stage hunk. ([github.com/gitui-org/gitui](https://github.com/gitui-org/gitui))
- **Trade-off:** *"Choose gitui if you… do not need interactive rebase or custom patches."* Less granular than lazygit (no per-line custom-patch building). ([qodo/stackshare synthesis](https://stackshare.io/stackups/gitui-vs-lazygit))
- **Lesson for zer0:** Rust-grade responsiveness matters in a TUI, but feature-depth (lazygit's per-line patches) is what reviewers reach for. `INFERENCE:` favor lazygit's depth; steal gitui's performance discipline.

## delta

- **Line diff, beautified:** *"syntax-highlights the diffed code"*, side-by-side, but *"delta mainly shows the lines that changed like git would by default with some extra highlighting."* ([HN/comparison synthesis](https://news.ycombinator.com/item?id=42091691)) A *pager/renderer*, not a reviewer. Great for readable output; copy its syntax-highlighted, side-by-side rendering layer.

## difftastic

- **Structural / syntax-aware:** *"a structural diff tool that compares files based on their syntax… If you reformat your code and it's now split over multiple lines, difftastic will show you what's actually changed."* It *"ignores formatting-only changes."* 30+ languages via Tree-sitter. ([github.com/Wilfred/difftastic](https://github.com/Wilfred/difftastic))
- **Lesson for zer0:** AI agents reformat aggressively; a structural diff that suppresses formatting-only noise is *especially* valuable for reviewing agent output, where the signal-to-noise problem is worse than human diffs. Strong candidate for the default diff engine.

## git builtin diff (baseline)

Line-oriented, no syntax highlighting, no structural awareness, pager-driven. The baseline everything above improves on. Not a model to copy — the reference point for "don't ship this."

## Agent-diff viewers (the directly-applicable references)

- **Zed AgentDiffPane** — *"multi-buffer tab with all changes… accept or reject each individual change hunk, or the whole set,"* with the *same keep/reject controls inline per file.* ([zed.dev/docs/ai/agent-panel](https://zed.dev/docs/ai/agent-panel)) **Best agent-review UX found.**
- **Cursor** — *"accept-per-file controls"* on a staged multi-file diff. ([digitalapplied](https://www.digitalapplied.com/blog/cursor-3-deep-dive-agents-composer-review-2026))
- **Cline** — inline per-action diffs + shadow-git checkpoints with three restore modes. ([cline docs](https://docs.cline.bot/features/auto-approve))
- **Vibe Kanban** — *"Review diffs and leave inline comments — send feedback directly to the agent without leaving the UI."* ([github.com/BloopAI/vibe-kanban](https://github.com/BloopAI/vibe-kanban)) The mid-task **redirect-via-comment** primitive.

# Synthesis — the five questions

### 1. Is anyone doing multi-agent orchestration WELL on Windows-native (not Mac-only / not WSL-only)?

**Essentially no — Warp is the lone exception, and it's a heavyweight cloud-tied terminal replacement.** The category is Mac-first:

| Tool | Windows-native? | Evidence |
|---|---|---|
| Conductor | No (Mac-only) | *"Run parallel coding agents on your Mac"* |
| Superset | No (macOS only) | *"OS: macOS (Windows/Linux untested)"* |
| Sculptor | Not yet | *"Windows support on the way"* |
| Claude Squad | No (tmux+gh) | tmux required; no Windows install path |
| Claude Code Agent Teams | Degraded | split-pane *"isn't supported in… Windows Terminal"*; needs WSL2+tmux |
| Vibe Kanban | Unclear + sunsetting | *"Build from source (macOS)"* |
| Cursor / Zed | Yes, but IDE | cross-platform editors, not terminal cockpits |
| OpenHands | Via Docker | not a native TUI |
| **Warp** | **Yes, GA** | `.exe` x64/ARM64, `winget install Warp.Warp` |

The white space is stark: **a Windows-native *terminal* cockpit coordinating Claude+Codex+Gemini as a team does not exist outside Warp**, and Warp is the opposite of lightweight/local. Even Anthropic's first-party Agent Teams can't render natively in Windows Terminal. `INFERENCE:` this is zer0's strongest, most defensible claim.

### 2. Is anyone POOLING shared memory/context across agents?

**Only Warp — and it's cloud/Warp-Drive-bound.** *"the only cross-harness memory system… can form memories from Claude Code and Codex sessions."* Every other tool is **isolation-first**: Conductor/Superset/Claude Squad/Crystal/Cursor/Zed all give each agent its own worktree/thread/context with **no shared store**. Zed states it outright: *"Each thread works independently with its own… context window, and conversation history."* Sculptor and Devin persist *per-session* context (resume), which is **not** pooling across agents.

So: pooled cross-agent memory is **near-virgin territory**, claimed only by Warp's cloud. A **local, event-sourced, cross-agent shared brain** (zer0's model) is unoccupied. This is white space #2.

### 3. Per-action approval gating vs post-hoc artifact/diff review — what do users actually prefer?

The split is clean and the evidence favors post-hoc for *parallel* agents:

- **Per-action gating** is the single-agent-IDE world: **Cline** (*"Every file edit and terminal command requires your approval"*). It does not survive volume — Cline itself ships granular **auto-approve** + **YOLO mode** to escape the prompts, and Roo Code won users by being *"for speed"* over Cline's gating. The friction is real and self-documented.
- **Post-hoc diff review** is the *parallel*-agent norm: Conductor, Superset, Cursor (accept-per-file), Zed (keep/reject hunks), Vibe Kanban, Devin. You cannot babysit 8 agents action-by-action.
- **Direct evidence of the shift:** *"When you have 100 agents executing thousands of daily actions, human review becomes the bottleneck… The answer is shifting to 'human-on-the-loop'—humans define boundaries, monitor patterns, and intervene on exceptions rather than approving every operation."* And the failure mode of forcing approval: *"skimmed diffs, rubber-stamped approvals, delayed merges without better quality."* ([attentive](https://www.attentive.com/blog/agentic-ai-governance-implementation); [codeongrass](https://codeongrass.com/blog/how-to-review-ai-generated-code-faster-than-you-can-read/))
- **The emerging preferred middle ground — "approve-with-comments":** *"you see the exact operation the agent wants to perform, and you can approve it, deny it, or approve it with a comment that redirects the agent mid-task without aborting the session."* ([codeongrass](https://codeongrass.com/blog/how-to-review-ai-generated-code-faster-than-you-can-read/)) Vibe Kanban's inline-comment-to-agent is the shipped version of this.

**Verdict:** post-hoc review is what users tolerate and what scales; per-action gating is a control feature for the paranoid/high-risk path, best offered as opt-in. This directly validates zer0's recorded decision (keep all 3 agents on AUTO, post-hoc Ctrl+R review, per-action as a dormant opt-in seam). The one upgrade the evidence demands: make post-hoc review **redirect-capable** (approve-with-comment), not just accept/reject.

## White-space gaps

Ranked by defensibility for a Windows TUI cockpit:

1. **Windows-native terminal team-cockpit.** No one nails Claude+Codex+Gemini as a *coordinated team* in a *native Windows terminal*. Mac tools dominate (Conductor, Superset, Sculptor, Intent); the tmux-based ones (Claude Squad, Claude Code Agent Teams) degrade to WSL2 and even corrupt Windows Terminal layouts. Warp is the only native option and it's a cloud-tied terminal *replacement*. **zer0 owns this slot if it renders independent agent lanes without tmux** (which the memory says it already does via alt-screen).

2. **Local, pooled cross-agent shared brain.** Everyone isolates; only Warp pools, and only in its cloud. A **local event-sourced shared memory** that lets Claude read what Codex learned (no cloud, no lock-in) is unclaimed. This is the feature competitors structurally *cannot* copy without abandoning worktree-isolation orthodoxy.

3. **Unified subscription-usage cockpit across heterogeneous agents.** Devin meters ACUs; Warp has its own billing; the worktree tools punt to each CLI. Nobody presents **one normalized "capacity remaining" view across Claude (5h/weekly), Codex (Plus quota), Gemini/agy** for a flat-subscription operator. zer0's usage-status-bar is genuinely differentiated — no competitor surfaced a unified subscription-capacity meter.

4. **Per-agent independence as a first-class UX (use free agents while one is busy).** The parallel tools fan out *copies of one prompt* (Cursor's 8-way, Superset's swarm) or isolate *tasks*. None foreground "agent A is busy, so talk to free agents B and C right now" as the core interaction. zer0's INV-0 (per-agent independence) is a distinct, unoccupied interaction model.

5. **Post-hoc review with mid-task redirect (approve-with-comment) in a terminal.** The hybrid the evidence says users want exists only in web UIs (Vibe Kanban). No terminal cockpit offers "review the diff, drop an inline comment, agent continues." Open slot.

6. **Co-equal Gemini.** Gemini/agy is a second-class citizen almost everywhere: Zed *"Gemini CLI… not currently supported"* over ACP; Warp Oz centers Claude/Codex; Conductor omits Gemini. A cockpit treating all three as **co-equal builders/reviewers** is rare. (Caveat: agy's ACP gap — antigravity-cli #31 — is the same wall Zed hit; zer0 shares this constraint, so the differentiation is "we support Gemini as a full agent anyway," via PTY today.)

**What is NOT white space (don't build here):** worktree isolation (commoditized — Claude Code's own desktop now ships it), generic kanban boards (Vibe Kanban sunsetting, Devin already owns the metaphor), and pure per-action gating (Cline owns it and users flee it via auto-approve).

## Best review interaction model to copy

**Synthesize three proven models into one terminal flow: lazygit's keyboard grammar + Zed's AgentDiffPane accept/reject-per-hunk + Vibe Kanban's approve-with-comment redirect, rendered with difftastic-style structural diffs.** Concretely:

1. **Entry — one keystroke to a unified review surface.** Mirror Zed: a `Review Changes` action (zer0's Ctrl+R) opens a **single multi-buffer pane aggregating every changed file across the agent's turn**, with a header summary *"which files, how many, how many lines"* (Zed's exact pattern). One agent's whole turn = one reviewable unit. This matches zer0's recorded post-hoc Ctrl+R review design.

2. **Navigation — lazygit's grammar, unmodified.** `j/k` move, `Enter` dive (file → hunks → lines), `Esc` up, `Tab` switch agent-lane/diff, `Space` to act on a hunk, `v` for a visual line-range, `a` for whole hunk. This is muscle memory for every terminal user already and is the densest, least-surprising keymap available. Do not invent a new one.

3. **Granularity — hunk-and-line accept/reject, per Zed.** *"accept or reject each individual change hunk, or the whole set."* Offer both the aggregate pane and an inline per-file mode with identical controls (Zed's dual-view). Per-file accept (Cursor) is the coarse fallback; per-hunk/line is the default.

4. **Rendering — structural diff to kill agent-reformat noise.** Use difftastic-style syntax-aware diffing so an agent's reflows/reformats don't drown the semantic change — *"ignores formatting-only changes."* Layer delta-style syntax highlighting + side-by-side for readability. This matters *more* for AI diffs than human diffs.

5. **The differentiating verb — approve-with-comment (mid-task redirect).** Beyond accept/reject, add Vibe Kanban's primitive in the terminal: on any hunk, leave an inline comment that is **sent back to the agent to redirect without aborting the turn** — *"approve it with a comment that redirects the agent mid-task without aborting the session."* This is the hybrid the scaling evidence says users actually want, and no terminal cockpit ships it.

6. **Safety net — Cline/Aider-style cheap undo, not pre-gating.** Back the post-hoc model with shadow-git checkpoints (Cline: *"commits the file state after each tool use"* + Restore Files/Task/Both) or Aider's auto-commit + `/undo`. Cheap, total reversibility is what *earns* the right to skip per-action gating. Keep zer0's dormant `PermissionDecider` seam for the opt-in high-risk path, but **default to AUTO + post-hoc review + instant rollback** — the evidence is unambiguous that this beats approval-fatigue.

**One-line model:** *Ctrl+R opens a lazygit-navigated, difftastic-rendered, Zed-style aggregate diff pane where you accept/reject per hunk or approve-with-a-comment-that-redirects-the-agent, all backstopped by one-keystroke checkpoint rollback.* That composite does not exist in any single shipping tool today — it's assembled from the best primitive of each, and it fits a Windows terminal cockpit precisely.
