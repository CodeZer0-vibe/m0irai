# Independent deep-research brief — multi-agent terminal experience & design

The multi-agent terminal cockpit should not feel like three chat windows crammed into a single tmux session; it must feel like a unified, orchestration-driven "super-agent." The terminal experience must prioritize the human as an editor and orchestrator rather than a passive reader of streaming text. By abandoning the traditional chat-bot paradigm in favor of progressive disclosure—hiding raw generation logs while surfacing actionable diffs, ambient cost/quota telemetry, and asynchronous queue states—the UI can achieve the legibility of a single-stream editor while wielding the combined power of Claude, Codex, and Gemini. 

## THRUST 1 — Users & the ideal terminal experience

**1. How power users ACTUALLY combine them today**
The current state of multi-agent workflows is defined by a "Speed vs. Reasoning vs. Context" division of labor. Power users rely on Claude (the reasoning layer) for architectural planning, zero-to-one scaffolding, and complex multi-file refactors. Because Claude burns through usage limits rapidly, developers manually pivot to Codex/GitHub Copilot (the speed layer) for tactical, sub-second line completions, boilerplate generation, and PR reviews within the IDE. Gemini (the context layer) is often treated as the high-quota overflow lane; developers dump massive log files, full documentation sites, or entire repositories into its million-token context window for brute-force analysis. Today, this is done via tedious copy-pasting between browser tabs, IDE sidebars, and CLIs. 

**2. What developers genuinely WANT**
Developers explicitly state they want "access to all the best models at once." But their unstated, implied desire is **zero context loss and zero manual routing**. They want to stop explaining the same architecture to three different models. ## Top recommendations (ranked)

1. **Build an Orchestrator, Not a Chat App:** Implement a unified input timeline where raw agent streams are suppressed by default. Use progressive disclosure (accordions) to hide reasoning and tool calls, surfacing only the final synthesized diffs or direct questions.
2. **Interactive `git-patch` Review Model:** Never auto-commit massive changes. Present all agent output through a `lazygit`-style interface where users can hit `y/n` to approve hunks, ensuring the human remains the final executive editor.
3. **Telemetry as a First-Class Citizen:** Dedicate a permanent ambient UI region (like `btop`) to real-time API cost, token context size, and rate-limit countdowns. Cost is the primary reason people use multi-agent setups; make it highly visible.
4. **Daemonized Background Agents:** Allow the main terminal to remain unblocked while an agent runs a long task. Push long-running tasks to an ambient status queue that the user can toggle into, ensuring true concurrent usage without UI freezing.

## What everyone gets wrong

**Assuming developers want to read AI reasoning in real-time.** 
The contrarian truth is that developers do not care about an agent's "chain of thought" unless something is broken. Most tools fall into the trap of streaming every token to the terminal, assuming speed of generation equals a good user experience. This creates extreme cognitive fatigue and terminal tearing. The right paradigm is a **Continuous Integration (CI) dashboard**: you don't watch the CI server compile every line of code; you watch a progress spinner, and you only look at the logs when the build fails. Stop treating agents like typing chatbots and start treating them like asynchronous worker threads.
